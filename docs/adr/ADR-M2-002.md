# ADR-M2-002：`VALIDATING` 為交易內狀態，執行進度以 BackgroundJob 為權威

日期：2026-08-04　狀態：ACCEPTED（適用 SLICE-M2-03 起的匯入驗證流程）

## 背景

里程碑 1 的 worker 以 `UPDATE import_batch SET status='VALIDATING'` 認領工作。
認領後崩潰即無人能重領，批次永久停在 `VALIDATING`——這違反設計書 §27.4 L1620
「任何非同步作業的失敗都不得讓業務物件停在中間狀態」。

同時，`catch (e) { quarantine(...) }` 把基礎設施故障（DB 瞬斷、物件儲存失敗）
判為 `QUARANTINED`，等於把執行失敗記成業務裁決。依基線 `QUARANTINED` 後須重傳新批次，
於是一次 DB 瞬斷會逼客戶重新上傳同一份檔案。

## 決定

1. **`VALIDATING` 是交易內的瞬時狀態。** `UPLOADED → VALIDATING → VALIDATED/QUARANTINED`
   （三個狀態、兩次遷移）全部收進同一交易，外部永遠觀察不到 `VALIDATING`。
2. **對外的執行進度以 `BackgroundJob` 為權威**，不是 `ImportBatch`：

       ImportBatch.status    = 業務結果狀態
       BackgroundJob.status  = 非同步執行進度（QUEUED/RUNNING/RETRY_WAIT/COMPLETED/FAILED）

3. **未來若 B-00 要顯示「驗證中」，由 `RUNNING` 的 job 推導**，
   不得改為等待 `ImportBatch` 出現 `VALIDATING`——那個狀態不會再出現。
4. 基礎設施故障不改 `ImportBatch.status`：批次維持 `UPLOADED`，job 走
   `RETRY_WAIT` → 重試耗盡 → `FAILED`。客戶不需重新上傳。

## 理由

§25.5 的七狀態機被完整遵守——兩次遷移都真實發生、都通過 `fn_import_batch_guard`。
改變的只是**可觀察性**，不是狀態機本身，因此不構成基線變更。

把進度可觀察性放在工作器物件上，正是設計書 §27.5 L1637 的位置：
「每個 run 產生階段性進度……使用者看得到卡在哪一步」。`ImportBatch` 是業務事實，
不該同時兼任執行進度看板——兩者混用正是「基礎設施故障污染業務狀態」的根源。

副作用是好的：「批次卡在 VALIDATING」**結構性消失**，而不是靠租約回收去補救。

## 代價與後續

- B-00 不再出現 `VALIDATING` 徽章。既有端到端測試不受影響（未斷言觀察到該狀態）。
- 部署前須確認既有停在 `VALIDATING` 的列並一次性人工處置；新流程不再產生這種列。
