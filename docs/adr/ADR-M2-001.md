# ADR-M2-001：退回里程碑與 `business_version` 的統一解釋

日期：2026-08-04　狀態：ACCEPTED（適用 SLICE-M2-02A 起的 Adjustment 實作）

## 背景

實作 Adjustment 生命週期時，兩份基線章節對「退回是否產生新版本」讀起來不一致：

| 出處 | 文字 |
|---|---|
| 設計書 §25.12 退回與例外矩陣（L910） | `PENDING_REVIEW → RETURNED → DRAFTING`：**「調整不換版」**；退回次數與理由進 KPI |
| 設計書 §26.9 三層版本語意（L1351） | `business_version` 的產生時機為**「提交、退回、覆核、批准等里程碑」** |

字面直讀會得到相反結論：一邊說退回不換版，一邊把退回列為 business_version 里程碑。

## 決定

兩者不矛盾，指的是不同層次。統一解釋為：

1. `adjustment_id` **不變**——退回不建立新的 Adjustment。
2. **不建立 superseding／替代調整**——這正是 §25.12「調整不換版」的意思。
3. 退回**是**業務里程碑，`business_version` **遞增**，並留下不可變的
   business-version snapshot 與退回事件（退回人、時間、原因分類、說明）。
4. 退回後的後續編輯由 `object_version` 處理，不產生 business_version 節點（§26.9）。
5. 重新提交、覆核、批准各自再形成後續 business version 里程碑。

## 理由

§25.12 該欄的標題是**「對版本與下游的影響」**，同欄其他列使用的措辭是
`version+1`（補件產生新批次）、`revision+1`（LOCKED → REOPENED）、
`期間不換 revision`（IN_REVIEW → IN_PREPARATION）。**整欄描述的是物件／修訂識別，
不是 §26.9 定義的稽核版本鏈。** 因此「調整不換版」= 不產生替代物件，
與 business_version 是否遞增無關。

反向驗證：若退回不進 business_version，§25.12 同時要求的「退回次數與理由進 KPI」
與 AC-WFL-001「退回、重開、管理員修改均有理由與時間」就失去不可變載體，
兩條要求會自相矛盾。故本解釋是唯一能同時滿足兩章的讀法。
