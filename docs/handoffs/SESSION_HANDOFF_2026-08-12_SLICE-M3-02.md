## 三條在本刀確立的原則

1. **權限是邊界，函式是流程，GUC 只是標記。** 自訂 GUC 任何連線都能
   `set_config`，不能當安全證據；批准欄以**欄位級權限**擋住（`app_runtime` 對
   `approved_by`／`approved_at` 連寫入通道都沒有）。
2. **只讀 Manifest 才叫可重演。** 「同一批現行資料跑兩次結果相同」只是確定性；
   AC-FX-001 要的是「現行主檔已變、只憑舊 Manifest 仍重算出原結果」。
3. **用 Manifest 之前先驗 Manifest。** 不可變 trigger 擋得住一般操作，擋不住
   資料修復、migration 或 owner 停用 trigger；驗證與生成共用同一套 canonical 規則。

## 測試紀律：本刀學到的四種假綠

反證是唯一能發現「測試通過的原因不是我以為的那個」的手段，但**反證本身也會被
環境架空**。本刀四次遇到「反證 0 條紅」，每一次都是測試的問題：

1. **不可逆的竄改排在中間**。0035 的「刪除一筆凍結條目」無法還原，排在中間時
   之後每個案例都因集合雜湊已不符而通過——三層檢查的反證全部 0 條紅。
   移到最後，並補兩個「只有該層抓得到」的竄改，三層才各自被釘住。
2. **反證產生同一個答案**。把 CTA 改成硬編 97,159.00 不會轉紅；要改成
   `+ 0.01` 才證明斷言釘的是值。
3. **斷言撞巧**。精度的重演證明必須用**乘積不整除**的案例——整除時
   0 位與 2 位得到同一個數，回查現行精度也看不出差別。
4. **被另一條守衛以相同訊息蓋掉**。來源 run 的期間檢查原本被批次歸屬檢查以
   同樣的 `§24.1A` 字串擋住；改成釘住它自己的訊息才有效。

另有兩個非反證的假綠：`INSERT … SELECT … LIMIT 1` 在空表上插入零列並「成功」；
`batchGate` 的 CVA 沒寫 `code` 欄，calculation-run 的 RBAC 斷言一直靠**其他套件
遺留的 CVA** 才通過（已補上穩定機器代碼）。
