### 0.1A 本版併入的變更請求：CR-002

CR-002（多案件日常作業模型，r4 `APPROVED_FOR_MERGE`）處理的問題是：v1.0 完整定義了**一個期間如何被正確處理**，卻沒有定義**一個人如何同時處理多個期間**。核心命題是**租戶隔離防的是「不該看到的人看到」，防不了「該看到的人放錯地方」**——一名職員對其被指派的六家客戶都有合法權限，D-24-01 的硬隔離與權限矩陣皆攔不住誤置。

| 落點 | 變更 |
|---|---|
| §24.1A | 新增「隔離 vs 歸屬完整性」的性質區分 |
| §24.6 | 權限矩陣補「身分人工確認」動作 |
| §24.7 | 新增 **SOD-07**（實例級：`resolved_by ≠ uploaded_by`）；編號沿革註明未回收 SOD-05 |
| §25.5 | 新增 `identity_status` **正交軸**；`ImportBatch.status` 七個主狀態**不增不減** |
| §25.13 | G-01 擴充為接受判定式 |
| §25.18 | 新增 `SourceIdentityResolutionPerformed` 事件 |
| §25.19 | 新增 D-25-06、D-25-07 |
| §26.6 | 新增 `SourceIdentityAssessment`、`SourceIdentityResolution`、草稿併發欄位 |
| §26.9 | 新增 `CalculationInputManifest`；ImpactAssessment 觸發來源補「身分重評估」 |
| §26.12 | 新增 **INV-28**（身分）與 **INV-29**（重演） |
| §27.4A | 新增併發控制與編輯來源識別 |
| §27.4／27.5 | 補草稿持久化、分段續傳、背景工作與 Session、manifest 重演 |

| §28.9 | 新增 `EngagementContext`、儲存狀態指示兩個共通元件 |

> **INV-29 是導出項，不是新需求**
>

## §24　系統邊界與角色圖

### 24.1 三層邊界：系統／責任／保存

要件手冊把「範圍內／第一階段不做」寫在同一張表裡，但其中混合了三種性質完全不同的邊界。基本設計必須先拆開，否則工程會把「平台不做」誤解成「平台不碰」，而合約會把「平台有存」誤解成「平台負責」。

| 邊界類型                         | 回答的問題           | 本平台的立場                                                                                                                                     | 誰有權變更               |
|----------------------------------|----------------------|--------------------------------------------------------------------------------------------------------------------------------------------------|--------------------------|
| **系統邊界** ／ System Boundary  | 哪些功能由平台實作？ | 收集 → 標準化 → 多基礎調整 → 折算與核對 → 輸出。**不含**日本日常記帳與申告、不含母公司總帳與完整合併引擎。                                       | 產品負責人               |
| **責任邊界** ／ Accountability   | 算錯了誰負責？       | 平台提供規則、計算與證據；**會計判斷責任屬事務所專業人員，政策與報表責任屬母公司管理層**。平台的自動結果一律為「建議」，經人批准才成為財務資料。 | 產品＋法務＋事務所合夥人 |
| **保存邊界** ／ System of Record | 正本在誰手上？       | MVP 預設**轉換副本**：日本正式帳簿與電子取引資料的正本仍在日本既有系統，平台保存具完整性驗證的受控副本與轉換證據。                               | 客戶＋法務（逐客戶）     |

> **設計落點：三軸向可追溯，不是三個欄位　\[v0.2 修正\]**
>
> 每個財務資料物件必須可沿**保存來源**、**加工血緣**、**批准責任**三個軸向完整追溯。單獨保存一個 `accountable_role` 不夠——日後必須能回答「哪一個自然人、以哪個組織的哪個角色、依哪一版政策、在何時批准」。

| 軸向     | 落點實體／欄位                                                                   | 必須能回答的問題                                                       |
|----------|----------------------------------------------------------------------------------|------------------------------------------------------------------------|
| **保存** | `SourceDataset`、`SourceDocument`、`system_of_record_ref`                        | 這個數字的正本在哪個系統、哪個檔案、哪一版、雜湊是否相符               |
| **加工** | 資料層級（raw／standardized／adjusted／translated／output）、版本、`LineageEdge` | 從來源列到輸出列之間經過哪些映射版、規則版與計算，可否反向重演         |
| **責任** | 實際使用者、**當時**角色、所屬組織、決策類型、批准政策版本、時間                 | 誰批准、以什麼身分批准、依哪一版政策批准、事後角色變更是否影響歷史紀錄 |

注意「當時角色」：角色指派會隨時間變動，批准紀錄必須凍結批准當下的角色與組織歸屬，不能靠 join 現行 RoleAssignment 推導。此點在 §26 會落成 `Approval` 的快照欄位。

### 24.1A 隔離 vs 歸屬完整性：兩種不同性質的控制　\[v1.1 新增・CR-002\]

> **租戶隔離防不了誤置**
>
> D-24-01 的硬隔離、RLS 與 §24.6 權限矩陣，處理的都是「**不該看到的人看到**」。但事務所的實際工作方式是一名職員同時被指派五到六家客戶——他對這六家**都有合法權限**。把 A 公司的檔案上傳到 B 公司，或在錯誤客戶下建立調整，這些操作**不越權**，因此隔離機制完全不會攔阻。

| 控制種類 | 防的是什麼 | 實作位置 | 失效時的徵狀 |
|---|---|---|---|
| **隔離控制** | 不該看到的人看到 | Tenant 邊界、RLS、權限矩陣、SOD-H1／H2 | 越權讀寫、跨租戶外鍵（INV-18） |
| **歸屬完整性控制** | 有權者把資料放到錯誤的客戶／法人／期間 | `EngagementContext` 伺服器端重新驗證、匯入身分比對（`identity_status`）、SOD-07 | 資料落在錯誤 Engagement，帳務正確但對象錯誤 |

**兩者不可互相替代，也不可合併實作。** 歸屬完整性的三條要求：

1. 每個作業畫面固定顯示客戶、法人與期間；多分頁各自維持獨立的 `EngagementContext`（§28.9）。
2. **伺服器必須重新驗證物件與 Engagement 是否一致，不得依靠使用者介面的下拉選單**——繞過 UI 直接呼叫 API 的請求必須同樣被擋下，並寫入 `ControlViolationAttempt`。
3. 匯入必須先宣告目標，再比對檔案內容（§25.5 `identity_status`、§26.6 `SourceIdentityAssessment`）。

### GB-02 補充：稅務基礎資料狀態

原草案寫成「B 只能從已申告的法人稅申告資料匯入」過窄。日本申告書通常在事業年度結束後才形成，母公司若按月或按季結帳，當時多半只有經稅務專業人員批准的稅務計算底稿或合理估計。因此判準是**可靠的稅務基礎與證據**，不是「申告書」這一種檔案形式。

| 狀態        | 意義                                           | 對下游的影響                                                                   |
|-------------|------------------------------------------------|--------------------------------------------------------------------------------|
| PROVISIONAL | 稅務計算底稿或合理估計，經指定稅務專業角色確認 | 可用於期中結帳與遞延稅試算；輸出時須標示為暫定並保留估計依據                   |
| FILED       | 已申告                                         | 可形成正式遞延所得稅結論；與先前 PROVISIONAL 的差異須產生差異說明              |
| AMENDED     | 更正申告後                                     | 觸發受影響期間的重算評估；歷史期間版本不覆寫                                   |
| MISSING     | 缺漏                                           | **硬性阻擋**正式遞延所得稅結論與期間包批准；系統標記缺漏、影響、負責人與截止日 |

法源待規則登錄簿（Part VIII）確認並版本化：ASBJ《中間財務諸表に関する会計基準》關於期中稅金費用合理估計之處理；ASBJ 稅効果會計適用指針關於一時差異為「會計上帳面金額與課稅所得計算上的資產／負債金額之差」之定義。本節僅作為設計約束，不構成個案稅務意見。

### 24.7 職責分離：實例級為主、角色級硬禁為輔

> **為什麼不是純角色級**
>
> 要件手冊 §10 指出「事務所可能僅有 2 至 3 名使用者，卻處理數十家客戶」。若把 SoD 全部實作成角色互斥，小型事務所會無法運作，實務上必然導致共用帳號——那才是真正的控制失效。但純實例級也不夠：有些禁令與工作量無關，屬於角色本身的性質，必須永遠成立。因此採**雙層**。

### 第一層：角色級硬性禁令（不可設定、不可豁免）

| 編號   | 禁令                                      | 實作點                                                                                             |
|--------|-------------------------------------------|----------------------------------------------------------------------------------------------------|
| SOD-H1 | R5 外部審計師永遠不得寫入或改變狀態       | 閘道層拒絕所有寫入；查閱與下載本身仍寫入稽核軌跡                                                   |
| SOD-H2 | R6 系統管理員不得編製、覆核或批准財務資料 | 技術性修正走「管理員例外變更」流程：工單編號、事由、事前授權，事後由 R4 確認；未確認者於證據包標示 |
| SOD-H3 | 規則發布者不得批准自己起草的規則版本      | `RuleVersion.drafted_by ≠ peer_reviewed_by`，平台層與 Tenant 層各自成立                            |

### 第二層：實例／狀態遷移級控制

| 編號   | 規則                             | 實作與例外處理                                                                                 |
|--------|----------------------------------|------------------------------------------------------------------------------------------------|
| SOD-01 | 編製人不得覆核自己編製的調整     | 比對 `Adjustment.prepared_by` 與 `reviewed_by`；相同即拒絕狀態遷移。**無論調整是否重大皆成立** |

### 第三層：人力不足時的處理順序（SOD-06）

> **SOD-01 是硬條件，補償性控制不能解除它　\[v0.3 修正\]**
>
> v0.2 原寫「兩者皆不可行時標記已交付但存在控制例外」，這與「SOD-01 無豁免」自相矛盾——若最終仍能交付，SOD-01 就不是硬條件。正確的處理順序是：
>
> **①** 引入母公司批准人（R4）擔任覆核　→　**②** 引入外部同行覆核　→　**③** 兩者皆不可行時，**不得形成正式交付**（`DELIVERED`），只能輸出帶有 `DRAFT／UNREVIEWED` 標記的**非正式預覽包**。
>
> 預覽包不建立正式交付紀錄、不計入期間完成度、不可作為母公司過帳依據，且檔案本身帶浮水印與標頭警語。

| 概念                     | 適用範圍                                                                                                                                                                   |
|--------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `WITH_CONTROL_EXCEPTION` | **已獲授權的軟性例外**：經批准的映射例外（未映射餘額）、經批准排除的資料缺漏項、尚未經 R4 確認的管理員例外變更。這些例外**有人批准過**，因此可以正式交付，但必須主動揭露。 |
| 非正式預覽包             | **硬條件未滿足**：SOD-01 無獨立覆核人、SOD-04 參與人數不足、G-01 借貸不平衡、G-03 B 基礎為 MISSING 且未經批准排除。這些情況**沒有人有權批准**，因此不能形成正式交付。      |

分界線：**「有授權者批准的例外」可以帶著揭露交付；「無人有權批准的缺陷」只能停在預覽。**經 R4 事前批准的流程降級（例如月次採兩段式）屬於政策而非例外，不列入任一類。

### 24.9 租戶隔離層級、信任邊界與跨境資料流

### Tenant 的定義與層級　\[v0.2 新增\]

**Tenant＝契約及最高資料隔離邊界，而不是固定等於某一種法人。**這個定義讓事務所型客戶與集團直客可以共用同一套模型。

    平台
    └─ Tenant　　　　　　　事務所工作空間／直客集團工作空間（契約與硬隔離邊界）
       └─ ClientEngagement　客戶集團或服務案件
          └─ LegalEntity　　日本子公司等法律實體
             └─ ReportingPeriod

| 原則           | 說明                                                                                             |
|----------------|--------------------------------------------------------------------------------------------------|
| 事務所型客戶   | 一間事務所通常一個 Tenant，內含多個 ClientEngagement                                             |
| 集團直客       | 一個企業集團可直接擁有一個 Tenant                                                                |
| Tenant 間      | **硬隔離**：資料、金鑰、權限、匯出範圍皆不互通                                                   |
| Tenant 內      | 不同 ClientEngagement 採**明示授權**，預設不可互見                                               |
| 升級隔離       | 若客戶契約、資料所在地或監管要求更嚴，可為該客戶建立**獨立 Tenant**                              |
| 身分與權限分離 | 使用者身分可跨 Tenant 共用，但權限必須透過 `TenantMembership` 與 `EngagementAssignment` 分別授予 |
| 規則庫層級     | `平台範本 → Tenant 共用規則 → Client 專屬規則`，作為 §26 的層級基線                              |

> `D-24-01`Tenant 粒度
>

> `D-24-03`R1 存取模式
>
> 支援直接登入的可選窄入口（上傳／查看驗證錯誤與補件要求／重新提交／查看自身提交狀態），亦可由客戶關閉改由 R2 代傳。無論何種模式，資料模型分別記錄 `provided_by` 與 `uploaded_by`。不新增第十個角色。

## §25　業務流程與狀態圖

### 25.1 設計立場

§24 把「誰可以做什麼」定了下來，但控制真正生效的地方是**狀態遷移**。SOD-01～04 不是介面提示，而是遷移的守衛條件；不滿足時遷移被拒絕，而拒絕本身要留痕。

| 原則                 | 說明                                                                                                                             |
|----------------------|----------------------------------------------------------------------------------------------------------------------------------|
| 狀態不可跳躍         | 所有遷移必須經過定義的邊；沒有「管理員直接改狀態」的後門（SOD-H2）。技術性修正走管理員例外變更流程，該流程本身是一條有紀錄的邊。 |
| 覆寫不刪除           | 手工覆寫不刪除原建議：原物件轉入 `SUPERSEDED` 並**必須**指向替代物件；沒有替代物件的作廢一律走 `VOIDED`。                        |
| 批准的對象必須已存在 | 批准不能指向尚未產生的結果。期間包最終批准的對象是一個確定的 `calculation_run_id`，不是「稍後會算出來的折算結果」。              |
| 可重演由執行紀錄保證 | 可重演性不靠流程順序，而靠 `CalculationRun` 完整記錄輸入版本集合（見 §25.3）。                                                   |
| 拒絕也是事件         | 守衛未通過時寫入 `ControlViolationAttempt`；但僅限狀態遷移與權限控制的拒絕，一般欄位驗證錯誤不進不可變軌跡（見 §25.18）。        |
| 例外必須可見         | 控制例外不得只存在於日誌，必須出現在期間狀態、交付紀錄與證據包三處。                                                             |

### 25.2 端到端流程：兩個批准節點

> **v0.1 的錯誤：把所有批准都放在折算前　\[v0.2 修正\]**
>
> 若 R4 在折算之前就完成全部批准，他實際上**沒有批准折算結果與折算差額**——而折算差額正是跨境轉換最容易出錯、也最需要覆核的數字之一。正確的做法是拆成兩個批准節點：**調整層批准在折算前**（決定要算什麼），**期間包批准在折算後**（決定算出來的東西可不可以交出去）。

    調整編製 → 調整覆核／批准 → 凍結計算輸入與匯率版本 → 執行折算（CalculationRun）
            → 折算核對 → 期間包最終批准（對象＝calculation_run_id） → 鎖定 → 輸出交付

![](assets/fig-25-1.svg)

*圖 25-1　期間泳道（前段）。⑨ 是調整層批准，批准對象是個別調整；期間包的最終批准在折算與核對之後（圖 25-2）。*

![](assets/fig-25-2.svg)

*圖 25-2　計算與交付鏈。每次重算產生新的 calculation_run_id；R4 批准的是某一個確定的 run，因此「批准了哪一組折算結果」永遠明確。*

### 25.3 CalculationRun：可重演性的載體

AC-FX-001 的「指定實體、期間與匯率版本重跑結果一致」不是靠流程順序保證，而是靠每次計算執行固定記錄其輸入版本集合。

    CalculationRun
    ├─ calculation_run_id
    ├─ period_revision              期間的第幾次修訂
    ├─ source_dataset_set           納入計算的來源批次集合
    ├─ adjustment_version_set       納入計算的調整版本集合
    ├─ mapping_version_set          映射版本集合
    ├─ rule_version_set             規則版本集合
    ├─ exchange_rate_version        匯率版本
    ├─ translation_policy_version   折算政策版本（期末／期中／歷史匯率之適用）
    ├─ materiality_threshold_set    重要性門檻版本集合
    ├─ engine_version               計算引擎版本
    ├─ executed_by / executed_at
    └─ status                       RUNNING / COMPLETED / FAILED / SUPERSEDED

| 規則         | 說明                                                                                                 |
|--------------|------------------------------------------------------------------------------------------------------|
| run 不可修改 | 任何輸入變動都產生**新的 run**，舊 run 保留。重跑同一 run 的輸入集合必須得到相同結果（AC-RUL-001）。 |
| 批准綁定 run | `PeriodApproval.calculation_run_id` 為必填。若批准後 run 因任何原因被取代，期間必須退回重新批准。    |
| 輸出綁定 run | `ExportJob.calculation_run_id` 與證據包共用同一 run，確保審計師拿到的證據對應該次輸出。              |
| 引擎版本入列 | 計算引擎升級也可能改變結果，因此 `engine_version` 必須是 run 的一部分，否則跨年度重演會失敗。        |

### 25.5 ImportBatch 匯入批次

    DRAFT ──上傳──▶ UPLOADED ──系統──▶ VALIDATING ──┬─失敗─▶ QUARANTINED ──重傳──▶（新版本 UPLOADED）
                                                    └─通過─▶ VALIDATED ──R2 接受──▶ ACCEPTED
    ACCEPTED ──同期間新版被接受──▶ SUPERSEDED（必須指向替代批次）

| 狀態          | 意義                                            | 離開條件與允許角色                          |
|---------------|-------------------------------------------------|---------------------------------------------|
| `DRAFT`       | 已建立批次，檔案尚未齊備                        | R1／R2 補齊必要檔案後提交                   |
| `UPLOADED`    | 檔案已落地，原始檔＋雜湊不可覆寫                | 系統自動進入驗證                            |
| `VALIDATING`  | 格式、借貸平衡、期間歸屬、重複與缺漏檢查        | 系統                                        |
| `QUARANTINED` | 驗證失敗，隔離但**不刪除**                      | 上傳修正版 → `version+1` 新批次，本批次保留 |
| `VALIDATED`   | 通過技術驗證，尚未納入期間                      | R2 接受；R3 可要求重驗                      |
| `ACCEPTED`    | 已納入該期間作為計算來源                        | 期間鎖定後不可再接受新批次（需先重開）      |
| `SUPERSEDED`  | 被較新批次取代，**必須存在 `superseded_by_id`** | 終態，永遠可查詢與比對                      |

> **provided_by 與 uploaded_by（承 D-24-03）**
>
> 每個批次同時記錄原始資料提供者與實際操作上傳者。補件通知、逾期統計與「補件輪次」KPI 一律以 `provided_by` 歸屬，否則 R2 代傳會讓 KPI 全部算到事務所頭上。

#### identity_status：與處理進度正交的第二個軸　\[v1.1 新增・CR-002\]

> **為什麼不放進主狀態機**
>
> 身分比對若寫成 `DRAFT → IDENTITY_CHECKED → PENDING_IDENTITY_CONFIRMATION → ACCEPTED`，就會與上表七個狀態形成**兩套互斥的狀態機**——`UPLOADED`、`VALIDATING`、`QUARANTINED`、`SUPERSEDED` 無處安放。身分比對描述的是「這份檔案屬於誰」，處理進度描述的是「這份檔案走到哪」，兩者正交，因此獨立成一個屬性。`IDENTITY_CHECKED` 適合作為事件與評估紀錄（`SourceIdentityAssessment`），不適合作為批次主狀態。

    ImportBatch.status     DRAFT → UPLOADED → VALIDATING →┬→ QUARANTINED
                                                          └→ VALIDATED → ACCEPTED → SUPERSEDED
                                    （七個狀態，v1.0 不變）

    identity_status        NOT_CHECKED → MATCHED
                                       → PENDING_CONFIRMATION → MANUALLY_RESOLVED
                                       → CONFLICT

| `identity_status` | 意義 | 產生方式 | 對接受的作用 |
|---|---|---|---|
| `NOT_CHECKED` | 尚未比對 | 初始值 | 不得接受 |
| `MATCHED` | 內容與宣告目標一致 | 權威識別符相符，或公司名稱命中已批准別名表 | 可接受 |
| `PENDING_CONFIRMATION` | 檔案缺少可靠識別資訊（`UNVERIFIABLE`） | 無權威識別符且未命中別名表 | 待人工確認 |
| `MANUALLY_RESOLVED` | 已由有權者確認並記錄理由 | 建立 `SourceIdentityResolution`，受 SOD-07 約束 | 可接受 |
| `CONFLICT` | 明確法人代碼或期間不一致 | **僅權威識別符可產生** | **硬性阻擋，無人工豁免**；主狀態可進 `QUARANTINED` |

**判定證據的強度分級**——名稱相似度本身不足以產生 `MATCHED`：

| 證據 | 可支持的判定 | 說明 |
|---|---|---|
| 權威識別符（法人番号、統一編號、契約內法人代碼、期間代碼） | `MATCHED` 或 `CONFLICT` | **唯一可以產生 `CONFLICT` 的證據等級** |
| 公司名稱 ＋ 已批准別名表（受管版本，R7 維護、R4 批准） | `MATCHED` 之證據 | 命中即記錄所用別名與別名表版本 |
| 僅模糊名稱相似 | 維持 `PENDING_CONFIRMATION` | 不得升為 `MATCHED`，也不得降為 `CONFLICT` |
| 無任何可辨識資訊 | `PENDING_CONFIRMATION` | — |

> **兩個不能犯的錯**
>
> 把 `UNVERIFIABLE` 當成 `MATCHED`，等於沒有控制。因為公司名稱少一個「株式会社」就直接封鎖，會讓使用者學會忽略警告。三值判定的存在就是為了避免被迫二選一。

**`CONFLICT` 不提供人工豁免。** 出路只有三條：修正宣告目標、重新上傳正確檔案、以新版識別規則重新偵測。理由與 SOD-01 一致——一旦提供豁免按鈕，控制就退化成提示。

**已 `ACCEPTED` 批次日後重新評估為 `CONFLICT`**：既有紀錄**不原地改寫**（歷史事實必須保存，INV-10），改為建立 `ImpactAssessment`，標記受影響的 `PeriodRevision` 與 `CalculationRun`，由 R3 覆核、R4 決定重開／更正／當期反映——**沿用 D-25-03 既有的影響評估機制，不另建第二套模型**。識別規則升版本身**不自動重評估**歷史批次（詳 D-25-07）。

### 25.6 TaxBasisDataset 稅務基礎（B）

| 狀態          | 意義                                           | 對下游的影響                                             |
|---------------|------------------------------------------------|----------------------------------------------------------|
| `MISSING`     | 缺漏                                           | **硬性阻擋**正式遞延稅結論與期間包批准（G-03）           |
| `PROVISIONAL` | 稅務計算底稿或合理估計，經指定稅務專業角色確認 | 可用於期中結帳；輸出與證據包須標示「暫定」並保留估計依據 |
| `FILED`       | 已申告                                         | 可形成正式結論                                           |
| `AMENDED`     | 更正申告後                                     | 觸發影響評估流程                                         |

### B 基礎新版本到達的處理流程（D-25-03）

    B 新版本到達
      → 比較內容雜湊及金額
      ├─ 完全相同（僅 PROVISIONAL → FILED）
      │     → 只更新證據成熟度，不產生財務重算，不建立 CalculationRun
      └─ 有差異
            → 產生 ImpactAssessment（受影響期間、科目、金額、是否超過更正門檻）
            → 標記受影響的 PeriodRevision／CalculationRun
            → R3 專業覆核
            → R4 決定：重開 ／ 當期反映 ／ 無需處理
            → 決定與理由寫入證據包

「只是成熟度提升、數字沒變」是實務上最常見的情形，若一律觸發重算會製造大量無意義的版本。因此以**內容雜湊與金額比對**作為分岔點。

### 25.7 Adjustment 調整

![](assets/fig-25-3.svg)

*圖 25-3　Adjustment 狀態機。轉回不是原調整的終態：原調整保持 LOCKED，另建一筆 ReversingAdjustment 以 reverses_adjustment_id 指回。這樣才能正確呈現「原分錄當期有效，後來於另一期間被轉回」。*

### 資料完整性條件

| 狀態         | 強制條件                                                                                                                   |
|--------------|----------------------------------------------------------------------------------------------------------------------------|
| `SUPERSEDED` | **必須**存在 `superseded_by_id`，且該物件存在並處於有效狀態。無替代物件者不得進入此狀態。                                  |
| `VOIDED`     | **不得**存在替代物件，但**必須**有 `void_reason` 與作廢人。                                                                |
| `LOCKED`     | 終態。轉回不改變此狀態；`reversal_status` 為衍生屬性（`NONE / SCHEDULED / REVERSED`），由 `ReversingAdjustment` 反向推導。 |
| `APPROVED`   | 批准快照凍結自然人、當時角色、所屬組織、政策版本與時間（承 §24.1 責任軸）。                                                |
| `ESCALATED`  | **必填 `escalation_reason`**（見下表）。升級不是「暫時擱置」，而是把判斷責任明確交給某個人。                               |

### escalation_reason：升級必須說出是哪一種升級　\[v0.3 新增・UI-25-01\]

v0.2 的 `ESCALATED` 只寫了「規則無法確定」一種來源，但實際上至少有六種，而它們的處理人與處理方式完全不同。若不分類，升級佇列會變成一個沒有人知道該怎麼清的清單。

| escalation_reason            | 典型處理人                  | 意義                                        |
|------------------------------|-----------------------------|---------------------------------------------|
| RULE_UNCERTAIN               | R2／R3                      | 規則適用條件無法確定，需專業判斷            |
| **INSUFFICIENT_GRANULARITY** | R1（補資料）或 R2（改人工） | 規則所需粒度高於實際 DataCoverage（INV-23） |
| MISSING_EVIDENCE             | R1／R2                      | 法源、附件或判斷理由不齊（G-08）            |
| DATA_QUALITY                 | R1／R2                      | 來源資料異常、重複或不一致                  |
| POLICY_CONFLICT              | R4                          | 兩條政策或規則對同一情形給出相斥結論        |
| AUTHORITY_REQUIRED           | R4                          | 需管理層決定（例如是否追溯重編）            |
| OTHER                        | 指定                        | 需填說明；比例過高時視為分類不足的訊號      |

#### INSUFFICIENT_GRANULARITY 的附加欄位

    rule_version_id           哪一條規則
    required_granularity      規則需要什麼（例如 JOURNAL）
    available_granularity     實際有什麼（例如 BALANCE）
    affected_account_scope    影響哪些科目
    data_coverage_id          依據哪一筆涵蓋紀錄判定
    resolution_requirement    補 GL ／ 改人工判斷 ／ 本期停用規則

> **INV-23 觸發時必須留下物件，不能靜默略過**
>
> 規則因粒度不足而不得自動執行時，**必須建立或更新一筆 `Adjustment` 並使其進入 `ESCALATED`**，指定「補 GL、改人工判斷或停用規則」三者之一為 `resolution_requirement`。
>
> **不得把「沒有運行」當成「結果為零」。**這是本節唯一一條同時寫進資料模型、狀態機與畫面規格的要求（§26 INV-23、本節、§28.8），因為它是最容易在實作時被省略的一種正確性。

### 25.9 DeliveryRecord 與 delivery_quality

> **交付品質屬於交付，不屬於期間　\[v0.2 修正\]**
>
> v0.1 把 `delivery_quality` 放在 `ReportingPeriod` 上，但期間狀況會持續變動（重開、補證據、例外解除），若品質標記跟著變，**歷史交付的品質就被追溯改寫了**。母公司三個月前收到的那一份，當時是什麼品質就永遠是什麼品質。

    DeliveryRecord（不可變）
    ├─ delivery_record_id
    ├─ period_revision_id           當時的期間修訂
    ├─ calculation_run_id           當時的計算執行
    ├─ export_run_id                當時的輸出執行
    ├─ delivery_quality             CLEAN / WITH_CONTROL_EXCEPTION
    ├─ control_exception_snapshot   當時未解除的例外清單（事由、金額、補償措施、責任人）
    ├─ delivered_to / delivered_at / delivered_by
    └─ status                       ACTIVE / WITHDRAWN / SUPERSEDED

期間畫面可以顯示「目前最新交付品質」，但那是對最新 `DeliveryRecord` 的查詢結果，不是期間自己的欄位。

### 輸出資格是兩個維度，不是一個列舉　\[v0.3 修正・UI-25-02\]

v0.2 把 CLEAN、控制例外與預覽包塞進同一組概念，結果混淆了兩件不同的事：**能不能輸出**與**輸出的品質**。實際上還有第三種情形——數字在算術上根本不成立——它連預覽都不該產生。因此拆為兩個獨立維度。

    output_capability = NONE | PREVIEW | OFFICIAL      能不能輸出
    delivery_quality  = CLEAN | WITH_CONTROL_EXCEPTION 輸出的品質（僅 OFFICIAL 適用）

| 情況                                 | output_capability | delivery_quality         | 說明                                                             |
|--------------------------------------|-------------------|--------------------------|------------------------------------------------------------------|
| 借貸不平衡、控制總額不符、計算不完整 | `NONE`            | 不適用                   | 可提供**診斷畫面或差異清單**，但不得產生看起來像財務報表的下載檔 |
| 數字成立但尚未覆核，或無合格覆核人   | `PREVIEW`         | 不適用                   | 帶 DRAFT／UNREVIEWED 浮水印，不建立正式交付紀錄                  |
| 有已批准的控制例外                   | `OFFICIAL`        | `WITH_CONTROL_EXCEPTION` | 可交付，但須在期間狀態、交付紀錄與證據包封面三處揭露             |
| 全部控制通過                         | `OFFICIAL`        | `CLEAN`                  | —                                                                |

> **為什麼 NONE 這一層必須存在**
>
> 一份借貸不平衡的檔案，即使標了 DRAFT 浮水印，仍然是有害的——收到的人不會每次都注意浮水印，而數字一旦離開系統就會被引用。**算術上不成立的輸出，比沒有輸出更糟。**此時應提供的是診斷資訊（差在哪一列、差多少），不是一份看起來像報表的檔案。

#### 形式化約束（§26 INV-27）

    output_capability ≠ OFFICIAL  →  delivery_quality IS NULL
    output_capability = OFFICIAL  →  delivery_quality ∈ (CLEAN, WITH_CONTROL_EXCEPTION)

**硬守衛與 output_capability 的對應**：G-01（借貸平衡）、G-09（控制總額）、G-07（匯率版本未凍結）、G-10（前期未銜接）明確設定 `output_capability = NONE`；G-04（SOD-01）、G-06（參與人數）、G-12（run 已被取代）設定 `PREVIEW`；G-02、G-03、G-08 在取得批准例外後可達 `OFFICIAL`＋`WITH_CONTROL_EXCEPTION`。

### 25.10 RuleVersion 三層生效鏈

    【平台控制面】
    TEMPLATE_DRAFT ─同行覆核─▶ TEMPLATE_REVIEWED ─發布─▶ TEMPLATE_PUBLISHED ─▶ DEPRECATED ─▶ RETIRED
                                        │ 產生「更新候選＋差異報告」，不自動改客戶版本
    【Tenant 控制面】                    ▼
    ADOPTED_DRAFT ─同行覆核─▶ TENANT_REVIEWED ─R8 批准─▶ TENANT_APPROVED
    【Client 層】                        ▼
    CLIENT_DRAFT ─(涉集團政策時) R4 確認─▶ EFFECTIVE(生效日) ─▶ SUPERSEDED ─▶ RETIRED
                                        ▼ 期間鎖定時凍結 rule_version_set（納入 CalculationRun）

| 遷移                            | 守衛條件                                                      |
|---------------------------------|---------------------------------------------------------------|
| TEMPLATE_DRAFT → REVIEWED       | SOD-H3：`drafted_by ≠ peer_reviewed_by`（平台層）             |
| TEMPLATE_PUBLISHED 發布         | 須附測試案例與來源依據；發布**不觸發**任何客戶資料重算        |

### 25.11 下游失效鏈：STALE → SUPERSEDED　\[v0.2 修正\]

> **v0.1 的錯誤：退回當下就標 SUPERSEDED**
>
> `SUPERSEDED` 的定義要求存在替代物件，但退回的那一刻替代成果還沒產生。因此必須引入中間狀態。

    上游被退回或改版
      → 下游結果標記 STALE ／ INVALIDATED（保留，但禁止交付）
      → R2 明示觸發重算
      → 新結果生成
      → 舊結果才轉為 SUPERSEDED（此時 superseded_by_id 才存在）

### 已交付檔案的三種處理

| 狀態                   | 情形                 | 對外意義                                                                     |
|------------------------|----------------------|------------------------------------------------------------------------------|
| `ACTIVE`（來源已重開） | 期間已重開但尚未撤回 | 仍是最後一次正式交付，但標記「來源期間已重開」，提示母公司後續可能收到替代檔 |
| `WITHDRAWN`            | 已明確通知收件人撤回 | 該次交付不再有效，母公司不應據以過帳；撤回通知本身留痕                       |
| `SUPERSEDED`           | 替代檔已正式交付     | 指向新的 `delivery_record_id`；此時且僅此時符合 SUPERSEDED 定義              |

不自動重算是刻意的：自動重算會讓「哪一版被覆核過」變得模糊，重算必須由 R2 明示觸發並重新走覆核。

#### G-01 的接受判定式　\[v1.1 新增・CR-002\]

    ImportBatch.status == VALIDATED
    AND identity_status IN (MATCHED, MANUALLY_RESOLVED)
    AND 完整雜湊驗證通過
    →  方可進入 ACCEPTED

三個條件缺一不可。`identity_status = CONFLICT` 者永遠不滿足第二項，因此**不可能**進入 `ACCEPTED`（INV-28）；`PENDING_CONFIRMATION` 者須先由有權者建立 `SourceIdentityResolution`（受 **SOD-07** 約束：`resolved_by ≠ uploaded_by`）。

**擴充既有 G-01，不新建守衛**——匯入驗證本來就是 G-01 的掛載點；另立 G-13 會讓「匯入為什麼被擋」分散在兩個編號下。

### 25.14 重要性門檻模型

單一通用門檻無法同時服務四種完全不同的判斷，因此門檻本身是分類的物件。

| 門檻類型                 | 用途                                 | 影響的守衛／決策              |
|--------------------------|--------------------------------------|-------------------------------|
| 調整批准門檻             | 判定調整是否「重大」                 | G-05（SOD-02 是否強制三段式） |
| 期間更正／重開門檻       | 判定已交付期間的錯誤是否須重開       | §25.15 更正政策決策表         |
| 映射與資料品質容許門檻   | 判定未映射餘額是否可放行             | G-02                          |
| 特定科目／高風險事項門檻 | 就特定科目類別或風險類別另設更嚴標準 | 覆寫上述任一類                |

### 粒度採繼承式覆寫

    ClientEngagement 預設值
    └─ LegalEntity 覆寫
       └─ PeriodType 覆寫（月次／季次／年次）
          └─ AccountClass / RiskCategory 特殊覆寫

採繼承而非笛卡兒積：只需維護有差異的層級，未覆寫者向上繼承。每個門檻必須記錄用途、幣別、絕對金額或百分比、有效期間與來源政策，且為**有版本的物件**，隨期間鎖定一併凍結（納入 `CalculationRun.materiality_threshold_set`）。

| 責任          | 內容                                                         |
|---------------|--------------------------------------------------------------|
| R7 建立／輸入 | 依母公司政策文件輸入門檻值與適用範圍                         |
| R3 檢查       | 一致性與適用性檢查（是否與既有期間衝突、是否與科目分類矛盾） |
| R4 批准       | 門檻屬管理層判斷，須由集團財務批准人批准後生效               |

### 25.15 更正政策 CorrectionPolicy

已交付期間發現錯誤時，走重開或次期更正不能只看重要性。決策表為版本化物件，提供**預設路徑**，但每次事件仍由 R4 作最終決定。

| 決策輸入                       | 取值                     |
|--------------------------------|--------------------------|
| 錯誤金額 vs 更正門檻           | 超過／未超過             |
| 母公司期間是否已關帳           | 是／否                   |
| 母公司是否已過帳               | 是／否                   |
| 報表是否已對外或向集團正式發布 | 是／否                   |
| 審計取證是否完成               | 是／否                   |
| 事項性質                       | 錯誤／估計變更／政策變更 |
| 母公司是否接受替換檔           | 是／否                   |

### 硬性原則

| 情形               | 處理                                                                                                       |
|--------------------|------------------------------------------------------------------------------------------------------------|
| 超過更正重要性門檻 | **不得自動採次期調整**，必須進入 R4 決策                                                                   |
| 尚未過帳或尚未關帳 | **預設重開並重新交付**                                                                                     |
| 已關帳／已發布     | 建立影響評估，由 R4 選擇重開或當期處理                                                                     |
| 會計分類           | 系統**不得**自動把次期處理稱為「前期損益調整」——錯誤、估計變更與政策變更的分類屬專業判斷，由人指定並附理由 |

### 25.16 期間流程分級

| 期間類型     | 流程                    | 條件                                                                       |
|--------------|-------------------------|----------------------------------------------------------------------------|
| 月次         | 編製 ＋ **獨立覆核**    | SOD-01 仍完全成立；須由 R4 **事前批准**為客戶工作流政策                    |
| 季次／年次   | 編製 ＋ 覆核 ＋ R4 批准 | 完整三段式，不可降級                                                       |
| 月次自動升級 | 升為三段式              | 出現重大調整、高風險規則、控制例外或政策變更時**自動**升級，不由使用者決定 |

> **authorize_for_delivery**
>
> 月次即使沒有 R4 逐筆批准，仍**必須有一位具交付權限的人執行 `authorize_for_delivery`**，把 `calculation_run_id` 明確認定為可交付。此權限可由 R3 擔任，但其正當性來自 R4 **預先批准的工作流政策**——政策本身是有版本的物件，並在證據包中揭露該期採用的流程等級。

### 25.17 跨期延續與首次轉換

    期間 N：LOCKED
      ├─ 期末餘額（各 BookBasis）─────▶ 期間 N+1 期初餘額（自動繼承，不可手改）
      ├─ 轉回排程 ───────────────────▶ 期間 N+1 自動產生 ReversingAdjustment 草案（SUGGESTED）
      ├─ 累積調整（永久性差異等）─────▶ 期間 N+1 延續，標示來源期間
      └─ 凍結版本集合＋CalculationRun ─▶ 供 N+1 差異比較與重演

期初餘額不可在 N+1 手動修改；若確有錯誤，必須重開期間 N（revision+1）。這是保證「N 期鎖定結果能正確銜接 N+1 期且差異可解釋」的唯一路徑（AC-PER-001）。

| 首次轉換步驟     | 內容與狀態影響                                                                                           |
|------------------|----------------------------------------------------------------------------------------------------------|
| ① 判定導入性質   | 新設／收購／同一控制／非同一控制／政策變更／單純更換工具。結果決定是否追溯重編，寫入客戶政策並需 R4 批准 |
| ② 建立歷史基準   | 收集最早必要日期的 A／B／C 基礎與歷史匯率。以特殊期間類型 `OPENING` 匯入，不參與一般月次流程             |
| ③ 一次性建立分錄 | 與日後重複規則分開標記（`is_one_time = true`），避免被誤判為每期複用的映射或規則                         |
| ④ 比較期間政策   | 是否追溯重編、與審計師的溝通紀錄，保存為客戶規則版本                                                     |
| ⑤ 期初橋接       | 產出「期初至當期期末」橋接底稿，成為第一個正常期間的 G-10 前提                                           |

## §26　領域資料模型／ERD

### 26.1 建模原則

| 原則                       | 說明                                                                                                                                                              |
|----------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 構成與調節分屬不同模型     | `BasisComposition` 用於**計算**某基礎，`BasisReconciliation` 用於**解釋**兩基礎之差。兩者數學性質相反，不共用實體——否則每個查詢都得記得排除另一種，遲早有人漏掉。 |
| 財務事實歸屬 ReportingUnit | 不是 LegalEntity。群組抵銷不屬於任何單一法人，必須有地方放。                                                                                                      |
| 幣別是關係不是鍵           | 同一 `BalanceSnapshotLine` 下掛多個 `TranslationResult`，以 `amount_role` 區分。固定雙欄會在遇到交易幣或第二報告幣時被迫改結構。                                  |
| 曆法與工作流分離           | `CalendarPeriod` 是曆法定義，`ReportingPeriod` 是工作流實例。同一套日本 4–3 月曆同時服務法定與稅務，靠 `CalendarUsage` 掛載，不複製日曆。                         |
| 只物化正式事實             | `JournalLine` 僅在 `Adjustment.APPROVED` 後存在。未批准的工作中資料留在 `AdjustmentLine`，只有 PREVIEW run 讀得到。                                               |
| 快照優於推導               | 覆核資格、參與者、批准角色、規則版本集合，全部在事件當下快照。任何需要「事後 join 現況才能回答」的問題，設計上就是錯的。                                          |
| 不變條件先於欄位           | §26.12 的不變條件是本節真正的產出；欄位清單只是實現它們的手段。                                                                                                   |

> **最小粒度：規定在政策，不是鎖在結構**
>
> P0 規定：**一般來源期間至少拆到月，所有來源事實必須帶 `accounting_date` 與 `source_calendar_period_id`**。但模型不要求「所有 CalendarPeriod 必須等於曆月」——以起訖日期為真實邊界，才容得下 4-4-5 曆、13 期制、期中收購與處分、短期事業年度、決算日變更與特別調整期間。

> **估計不是期間組成**
>
> `ESTIMATED` 不放在 `PeriodCompositionItem`。「來源期間如何被納入」和「產生了一筆估計事實」是兩件事；混在一起，真實來源資料與人為估計會變成同一種東西。估計走 `Adjustment` 的 `estimation_method` 或獨立的 `PeriodEstimate`。
>
> `ALLOCATED_FLOW` 只能用於流量性科目，因此 `Account` 必須帶 `balance_behavior` = STOCK／FLOW。資產負債表是時點餘額，不能按月份比例分攤。

### ReconciliationDifference：狀態在欄位裡，不在實體名稱裡

原命名 `UnexplainedDifference` 有一個缺陷：一旦原因確認為尾差或時間性差異，它就不再是 unexplained，但實體名稱已經把狀態寫死了。改以 `reason_class` 與 `resolution_status` 承載，「還有多少未解釋差異」一律查 `resolution_status = OPEN`，不依實體名稱或原因分類判斷。

    ├─ TranslationResult［］                       功能幣與報告幣各一
    ├─ reason_class = UNEXPLAINED | ROUNDING | TIMING | MAPPING

    ├─ resolution_status = OPEN | EXPLAINED | RESOLVED

|----------------|-----------------------------------------------------------------------------------------------------------------------------------------|

### 26.7 D　稅務：時點與流量必須分開

> **為什麼不能用單一 TaxYearAllocation**
>
> B 基礎中的資產／負債稅務基礎是**某個日期的存量**。把年度申告數字按月份比例分攤到 12/31，在概念上就是錯的——12/31 的稅務基礎應該是該日的暫定稅務基礎，不是年度數字的九個月比例。期中稅金費用才是流量，才有估計與分攤的問題。

#### 三層版本語意：不可混用　\[v1.1 新增・CR-002\]

自動儲存引入之後，「版本」一詞在本設計書中必須嚴格區分三種意義。混用會直接破壞可重演性——凍結一個**內容會變動**的識別碼，等於沒有凍結。

| 層 | 產生時機 | 用途 | 不是什麼 |
|---|---|---|---|
| `object_version` | 每次自動儲存遞增 | **併發控制** | **不進版本鏈**、不可稽核，不保證內容留存 |
| `business_version` | 提交、退回、覆核、批准等**里程碑** | **可稽核的正式版本鏈** | 不隨自動儲存增長；一小時的編輯不會產生數百個節點 |
| `CalculationInputManifest` | 建立 PREVIEW／OFFICIAL run 當下 | **凍結實際納入的輸入內容與雜湊** | 不是通用快照機制，只服務可重演性 |

> **這是把既有的 frozen set 做完整，不是另造一套機制**
>
> v1.0 的 `CalculationRun` 已要求凍結集合，但當時的隱含假設是「被凍結的識別碼指向不可變內容」。草稿層引入自動儲存後該假設不成立：`adjustment_version_set` 指向的 `AdjustmentLine` 仍會被後續自動儲存改寫。因此凍結集合必須自己保存**內容雜湊與內容本體**（或不可變引用），而不是只記一個識別碼。仍然不需要資料庫長交易，也不需要鎖住整個期間。

**重演的比較對象**：重演時必須取得 manifest 所保存或引用的**不可變凍結內容**，重新計算其 `content_hash` 並與 manifest 記錄比對。**目前工作物件與 manifest 不同屬正常情況，不構成重演失敗**——草稿本來就會繼續前進。只有凍結內容遺失、損壞或雜湊不符才是失敗，且**不得改讀目前工作物件並宣稱重演一致**（INV-29）。

### 26.15 決議紀錄

> D-26-01建立 CONSOLIDATION_GROUP 的 ReportingUnit
>
> 即使 MVP 只有母子兩個成員也要建，用途嚴格限制為 `snapshot_purpose = CONSOLIDATION_ADJUSTMENT_PACKAGE`，**不得產生 CONSOLIDATED_FINANCIAL_STATEMENT**。`GroupMembership` 必須有效期間化，否則未來成員加入、退出或持股變更無法回放。

> D-26-02科目表加一層版本化 ChartOfAccounts
>
> Account 不直接掛 Engagement，而是 `ChartOfAccounts → ChartOfAccountsVersion → Account`。集團科目表由 ClientEngagement 所有，日本法定科目表由 LegalEntity 或來源系統所有；Tenant 只保存 `ChartTemplate` 與 `MappingTemplate`，不保存任何客戶的正式科目。`MappingRule` 連接明確的來源與目標科目表版本。

> D-26-03資料粒度影響功能可用性，不只是揭露
>
> TB 每期必要；GL 可依科目、交易類型、重要性協商。但**規則需要 JOURNAL 而該範圍只有 BALANCE 時，該規則不得自動執行**（INV-23）。AC-AUD-001 的「可反查來源」須分為**餘額級／分錄級／憑證級**三種達成度，不得籠統宣稱達成。
>
> 落點：`SourceDataset.granularity`、`DataCoverage`（account_scope × date_range × granularity × completeness_status）、`Rule.required_granularity`。粒度降低會造成明確的功能降級，而不是默默降低審計證據品質。

> D-26-04保存期政策驅動，不是「永久保存」
>
> 完成的 OFFICIAL run 完整保存 SnapshotLine、TranslationResult、調節與證據索引，依客戶保存政策保存，**保存期內不可覆寫**。PREVIEW run 依 Tenant 政策設 TTL，到期後保留 manifest、版本集合、雜湊、建立者與時間，刪除大體量計算結果。Legal hold 與審計保全期間不得清除；正式資料到期刪除前須支援退出導出（INV-26）。
>
> 邏輯模型放 `retention_policy_id`、`expires_at`、`legal_hold`；實際保存多久留給契約與部署 ADR。

> D-26-05ROUNDING_TOLERANCE 不是普通財務重要性
>
> 尾差通常是幣別最小單位或明確絕對金額，不宜直接套用「財務重要性百分比」。scope 為 `ReportingUnit → CurrencyPair → TranslationMethod → AccountClass → OutputProfile`，與一般重要性門檻分開設定與批准。原因經系統證實為純算術尾差、且單筆與累積值皆在已批准容許範圍內時，可自動標記 `RESOLVED_BY_POLICY`——紀錄仍完整保留（INV-24）。

> D-26-06功能幣有效期間化
>
> 功能幣即使不同時存在多個，仍可能隨時間變更。改為 `ReportingUnitCurrencyAssignment`（role × currency × 有效期間 × 批准）；同一單位同一時點只能有一個 FUNCTIONAL；不同功能幣的分公司或海外營運單位建成獨立 ReportingUnit；ReportingUnit 上的 `current_functional_currency` 僅為快取。CalculationRun 凍結所使用的指派（INV-22）。

## §27　系統模組與整合架構

### 27.1 架構原則

| 原則                  | 說明                                                                                                                                                            |
|-----------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 模組化單體先於微服務  | 先確立資料所有權、契約與非同步邊界；部署形態可以晚決定，模組邊界不行。反過來做，會把還沒穩定的資料契約凍結成網路 API。                                          |
| 領域所有權唯一        | §26 的每個實體**恰有一個模組為 owner**。其他模組只能經契約讀取，不得直接寫入他人的表——這是日後能否安全拆分的唯一前提。                                          |
| 抽象邊界先於實作選型  | 凡是 ADR 尚未決定的，先定介面：`KeyProvider`、`ImmutableAuditStore`、`RuleEvaluator`、`ObjectRetentionStore`、`FileExchangeAdapter`。替換實作不得改動領域模型。 |
| 控制在服務層，不在 UI | §25 的守衛條件由 Workflow／Control 模組統一裁決。畫面上的禁用只是體驗，不是控制——AC-SEC-001 的越權測試會直接打 API。                                            |
| 計算不在請求執行緒    | `CalculationRun` 一律非同步。理由不只是效能：同步計算會誘使人在請求逾時後重試，而重試必須不產生第二個 run（INV-17）。                                           |
| 租戶隔離是橫切關注    | 不由各模組自行實作。隔離由資料存取層與 `TenantContext` 統一強制，否則 INV-18 會在第 N 個模組上被遺忘。                                                          |
| ERP 解耦              | 轉換核心不得依賴任何金蝶版本；適配器只處理欄位、格式、維度與傳輸（§16）。                                                                                       |
| 確定性重於效能        | 計算工作器禁止 wall-clock 與隨機來源；同一凍結集合重跑必須得到相同結果。任何為效能引入的快取都必須以 `calculation_run_id` 為鍵。                                |

      ├─ 拒絕：寫入 ControlViolationAttempt
      └─ 通過：呼叫物件所屬模組套用狀態遷移

> **交易語意：裁決與套用必須不可分割**
>
> 下列動作必須在同一交易語意內完成，否則守衛通過後、狀態實際更新前，資料可能已被另一個請求改變：
>
> `讀取目前 object_version → 守衛裁決 → 套用狀態 → 寫入 Approval／ParticipationEvent → Audit outbox`
>
> 樂觀鎖以 `object_version` 為基礎；版本不符即整筆重試裁決，不得只重試套用。

**「唯一寫入點」的範圍要限定清楚**：M7 是 **G-01～G-12 狀態遷移守衛的拒絕事件**的唯一寫入點。一般權限拒絕、RLS 拒絕、物件儲存拒絕仍會發生在 M1、資料庫或儲存層——這些不經過 M7，但最後都必須匯入 M10 的統一稽核介面。

### M4 與 M5 的邊界：模組分開不足以防止繞過

`BasisComposition` 放在 M4（政策）而 `BookBasis` 放在 M5（會計結構）是對的，但真正防止繞過 R4 批准的不是模組分開本身，而是下列**模組契約**——否則在同一個單體內仍可跨模組直接寫表。

| 契約                        | 說明                                                                         |
|-----------------------------|------------------------------------------------------------------------------|
| 只允許版本化                | M4 只接受版本化的 BasisComposition，不存在「就地編輯」的資料形態             |
| 不提供修改 EFFECTIVE 的介面 | M4 的 API 沒有「修改已生效版本」這個動作可呼叫                               |
| 生效必經 M7                 | 版本生效是一次狀態遷移，因此必然經過守衛與批准                               |
| 下游只讀 EFFECTIVE 或已凍結 | M5／M6 只能讀 EFFECTIVE 版本或已被 CalculationRun 凍結的版本，讀不到草案     |
| 禁止工具直寫                | 資料庫與管理工具不得直接更新政策表；技術性修正走管理員例外變更流程（SOD-H2） |

### 27.4 同步與非同步邊界

| 作業                                     | 形態       | 理由與約束                                                           |
|------------------------------------------|------------|----------------------------------------------------------------------|
| 登入、授權、查詢                         | \[同步\]   | —                                                                    |
| 狀態遷移與守衛裁決                       | \[同步\]   | 使用者必須立即知道被擋下與原因；拒絕同時寫入 ControlViolationAttempt |
| 映射編輯、調整編製                       | \[同步\]   | —                                                                    |
| 檔案上傳落地與雜湊                       | \[同步\]   | 必須在回應前完成，否則使用者不知道檔案是否真的收到                   |
| **草稿自動儲存**                         | \[同步\]   | 必須同步回傳伺服器確認——**只有取得確認才可顯示「已保存」**。連線正常時任一輸入內容須在窗口 W 內取得確認（MVP 暫定 5 秒，可經批准放寬至 10 秒）\[v1.1・CR-002\] |
| **分段上傳與續傳**                       | \[同步\]   | 每個分段取得接收確認；**完整雜湊驗證完成前不得標記為 `UPLOADED`**。未完成傳輸者可從已確認分段續傳\[v1.1・CR-002\] |
| **身分一致性比對**                       | \[非同步\] | 隨匯入驗證執行，產生 `SourceIdentityAssessment`。結果進入 `identity_status`\[v1.1・CR-002\] |
| 匯入驗證（格式、平衡、重複、缺漏）       | \[非同步\] | 大型 GL 可能數十萬列。批次進入 `VALIDATING`，完成後推播              |
| **CalculationRun**                       | \[非同步\] | 一律非同步。冪等鍵為 `calculation_run_id`；重試不得產生第二個 run    |
| 調節與差異偵測                           | \[非同步\] | 隨 CalculationRun 完成觸發                                           |
| 輸出產生與證據包打包                     | \[非同步\] | precheck 同步回報結果，實際產生非同步；兩者共用 run_id               |
| 影響評估（B 新版本、規則更新、來源改版） | \[非同步\] | 觸發後產生 ImpactAssessment，**不自動重跑**                          |
| 通知                                     | \[非同步\] | 失敗不得影響業務交易                                                 |
| 保存期執行與清除                         | \[非同步\] | 排程作業；`legal_hold` 為硬性跳過條件（INV-26）                      |

**前端關閉的邊界**：檔案**取得伺服器接收確認之後**，其驗證、解析、匯入與背景計算不因瀏覽器關閉或 Session 到期而中止；**接收確認之前**的位元組傳輸在純瀏覽器架構下無法保證，只能靠分段續傳把損失降到最小。Session 到期時先重新驗證身分再返回原畫面，已在背景執行的工作不受影響。\[v1.1・CR-002\]

### 27.4A 併發控制與編輯來源識別　\[v1.1 新增・CR-002\]

v1.0 的樂觀鎖主要針對狀態遷移，不足以定義草稿如何共同編輯。

| 項 | 規則 |
|---|---|
| 1 | **不鎖整個期間**——否則兩個人無法同時處理不同調整 |
| 2 | 以 `Adjustment` 或工作物件為併發控制粒度 |
| 3 | 每次保存帶 `object_version`、`base_object_version`、`edit_session_id`、`client_save_sequence` |
| 4 | **版本不符時，不得由最後寫入者直接覆蓋**；顯示誰在何時改了哪一版，提供比較、重新載入或另存 |
| 5 | 衝突判定以**其他編輯來源**為準——不是「他人」 |
| 6 | 同一 `edit_session_id` 的連續自動儲存**不得**觸發衝突畫面 |
| 7 | 相同 `client_save_sequence` 的重送由伺服器去重，不判定為衝突 |

> **同一個人開兩個分頁，是兩個編輯來源**
>
> 若以「使用者」判定衝突，同一人在兩個分頁編輯同一調整時，後寫入者會靜默覆蓋前者——而這正是多案件併行作業最常發生的情境。因此判定單位是 `edit_session_id` 而非 `actor_id`。

**自動儲存與樂觀鎖的交互**：自動儲存遞增 `object_version` 供併發控制，但**不產生 `business_version` 節點**（§26.9）——否則一小時的編輯會製造數百個可稽核版本。第一版**不需要**即時協作編輯；物件級樂觀鎖加上衝突畫面即足夠。

非同步作業的共同要求：具冪等鍵、可重試、失敗有明確終態與人可讀原因、進度可查詢、不吞掉錯誤。任何非同步作業的失敗都不得讓業務物件停在中間狀態——這是 §25「狀態不可跳躍」在架構層的對應要求。

### 27.5 計算工作器

    工作器契約
    ├─ 輸入：calculation_run_id（其凍結集合已完整寫入且已計算 content_hash）
    ├─ 禁止：wall-clock 讀取、隨機來源、外部即時查詢、未凍結的參數
    ├─ 冪等：同一 run_id 重複派工必須產生相同結果或直接返回既有結果
    ├─ 逾時：逾時後 run 進入 FAILED，不得留在 RUNNING；失敗原因人可讀
    └─ 輸出：BalanceSnapshotLine ＋ TranslationResult ＋ 調節輸入，全部帶 run_id

| 議題       | 設計                                                                                                                                                                                 |
|------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 確定性     | 凍結集合＋`engine_version` 決定一切輸入。工作器不得讀取「目前的」任何東西——這是 INV-17 在執行層的要求，也是 AC-RUL-001「同一輸入與同一版本重跑必須得到相同結果」唯一可靠的保證方式。 |
| 租戶公平性 | 佇列必須避免單一大租戶佔滿所有工作器。至少採每租戶並行上限；年度結帳期的尖峰是可預期的，不能讓一家客戶的年結卡住其他客戶的月結。                                                     |
| 優先序     | OFFICIAL run 優先於 PREVIEW run；同類型內按提交時間。優先序不得由使用者自行調整。                                                                                                    |
| 隔離       | 預設共用工作器進程池；大型或高風險客戶可指定專用工作器（ADR-04）。                                                                                                                   |
| 可觀測性   | 每個 run 產生階段性進度（讀取、映射、規則、折算、快照寫入），使用者看得到卡在哪一步，而不是只有一個轉圈。                                                                            |

#### 重演與 manifest　\[v1.1 新增・CR-002\]

計算工作器建立 run 時，一併寫入 `CalculationInputManifest`：凍結每一筆輸入的 `object_id`、`object_version`、`content_hash` 與不可變內容（或不可變引用），並記錄 `hash_algorithm` 與 `canonicalization_version`。

    重演流程
    ├─ 讀取 manifest（不讀目前工作物件）
    ├─ 取得每筆 entry 的凍結內容或不可變引用
    ├─ 以 manifest.hash_algorithm ＋ canonicalization_version 重算 content_hash
    ├─ 比對 → 不符／遺失／損壞　⇒　REPLAY_FAILED（外顯，不得靜默改讀現況）
    └─ 相符　⇒　以凍結內容重算，結果必須與原 run 相同

**PREVIEW 執行期間繼續編輯是允許的**，編輯產生新的 `object_version`（**非** `business_version`），既有 run 的 manifest 不受影響。想看修改後的結果就建立新的 PREVIEW run；舊 run 保留至其保留期限（D-26-04）。

`immutable_payload_ref` 若指向外部儲存體，該儲存體必須保證不可變且在保留期內可取得——此需求落在 ADR-03（`ObjectRetentionStore`）的抽象邊界上。

### 27.8 部署候選

> #### 背景
>
> D-24-01 定義 Tenant 為契約與最高資料隔離邊界，Tenant 間硬隔離、Tenant 內 ClientEngagement 明示授權。INV-18 進一步要求不允許任何跨 Tenant 外鍵。同時事務所型客戶會在一個 Tenant 內服務數十個客戶案件，且平台級規則範本必須能跨 Tenant 複用。
>
> #### 決策驅動因素
>
> 隔離強度與可證明性（AC-SEC-001 的越權測試）／營運成本與 schema 演進成本／DEP-B 升級隔離的搬移難度／平台範本與租戶資料的共存／審計說服力。
>
> #### 候選方案與比較
>
> | 方案                          | 隔離強度 | schema 演進 | 備註                                                           |
> |-------------------------------|----------|-------------|----------------------------------------------------------------|
> | A 共用 schema＋應用層過濾     | 低       | 易          | 隔離仰賴「每個查詢都記得加條件」，一次遺漏即越權；審計難以證明 |
> | **B 共用 schema＋資料庫 RLS** | 中高     | 易          | 隔離由資料庫強制；風險在連線池的脈絡洩漏                       |
> | C 每租戶獨立 schema           | 高       | **難**      | 數十個租戶時每次遷移要對所有 schema 執行；平台範本需另置       |
> | D 每租戶獨立資料庫            | 最高     | 難          | 營運成本高；適合作為少數客戶的升級選項而非預設                 |
>
> #### 目前建議
>
> **B 為預設，D 作為升級隔離選項。**選 B 而非 A 的關鍵不是技術偏好，而是**可證明性**——「隔離由資料庫強制」和「隔離由每個開發者的紀律維持」在審計對話中是完全不同的兩件事。不選 C 是因為它會讓 DEP-B 的搬移從部署設定變成資料庫工程。
>
> #### 正面後果
>
> 越權測試可針對資料存取層集中驗證；DEP-A→DEP-B 的搬移路徑清楚；平台範本置於非租戶範圍即可跨 Tenant 複用。
>
> #### 負面後果與風險
>
> **連線池脈絡洩漏是頭號操作風險**，但不是唯一的致命模式。RLS 方案必須同時滿足下列八項，缺一項就會出現繞過路徑：
>
> | 項目             | 要求                                                                                        |
> |------------------|---------------------------------------------------------------------------------------------|
> | 資料庫角色權限   | 應用程式使用的資料庫角色**不得擁有 BYPASSRLS 或表格 owner 權限**——owner 天生不受 RLS 限制   |
> | fail-closed      | 沒有 TenantContext 時回傳零筆或直接拒絕，**不得視為全域查詢**                               |
> | 脈絡生命週期     | 租戶脈絡為 **transaction-local**，不依賴長期 session 狀態                                   |
> | 背景工作器       | 每個 job 重新解析並驗證 tenant_id，不繼承派工端的脈絡                                       |
> | 新增表與分區     | 分區表與新增子表必須**自動檢查是否已套 RLS**；漏套一張新表就是一個洞                        |
> | 鍵設計           | 外鍵與唯一性鍵最好包含 tenant_id，避免跨租戶關聯在資料層成立                                |
> | 資料庫以外的元件 | **Cache、Queue、Object Storage、Search Index、Log 不受資料庫 RLS 保護**，必須各自帶租戶範圍 |
> | 平台控制面       | 使用**獨立資料庫身分**與明確 break-glass 流程；不可讓一般平台帳號自然繞過 RLS               |
>
> 連線池的緩解措施：脈絡設定與清除由框架強制（`TenantContext` 不得由業務程式碼手動操作）、連線取得時強制重設、「跨租戶讀取」納入自動化測試的必測項。
>
> #### 安全與法規影響
>
> 對應 NFR-SEC-001、AC-SEC-001。平台控制面角色（PlatformRoleAssignment）必須與租戶控制面完全分離，否則 RLS 會被平台角色繞過。
>
> #### 遷移與退出
>
> 單一 Tenant 搬移至獨立實例（DEP-B）：因所有資料已帶 tenant_id，可按租戶匯出並載入新實例；退出導出（IF-12）本身即為此路徑的一部分。
>
> #### 重新檢討觸發條件
>
> ① 客戶契約要求資料庫層級的物理隔離；② 監管要求特定資料所在地；③ 單一租戶資料量或負載影響其他租戶；④ 發生任何跨租戶讀取事件。
>
> #### 關聯
>
> NFR-SEC-001、AC-SEC-001、D-24-01、INV-18、DEP-A／B／C

> ### ADR-02部署區域、資料跨境與儲存拓撲
>
> **狀態**　\[PROPOSED\]　**影響**　DF-1／DF-2、NFR-DATA-001、ADR-03、ADR-09
>
> #### 背景
>
> §24.9 已確立：無論部署在哪，**日本端必須保有能迅速顯示與輸出的路徑**，且不依賴平台單方可用性。日本帳簿保存制度要求保存場所能迅速顯示及輸出，但未要求伺服器物理位於日本。DF-2（平台→中國母公司）是跨境傳輸，須有法律依據與紀錄。
>
> #### 決策驅動因素
>
> 來源資料量集中在日本側／DF-1 是否跨境／中國端使用者延遲／CalculationRun 的原子性與可重演性／法務與客戶契約。
>
> #### 候選方案與比較
>
> | 方案                               | DF-1 跨境 | 可重演性 | 備註                                           |
> |------------------------------------|-----------|----------|------------------------------------------------|
> | **A 單一區域（日本）**             | 否        | 單純     | 來源資料就地處理；中國端使用者有延遲           |
> | B 單一區域（中國境內）             | 是        | 單純     | 日本帳簿資料全量跨境，DF-1 的合規負擔顯著上升  |
> | C 雙區域（日本存來源、中國存輸出） | 否        | **複雜** | 計算若跨區域，凍結集合的一致性與原子性難以保證 |
> | D 單一區域（第三地）               | 是        | 單純     | 兩端皆跨境；除非客戶明確要求，否則無優勢       |
>
> #### 目前建議
>
> **A（日本）為預設。**理由是量最大的資料流（DF-1）因此不跨境，且日本端「迅速顯示與輸出」的要求最容易滿足。DF-2 仍為跨境，但它是**受控且有限的輸出**（IF-07／08），逐次記錄法律依據、接收方範圍與傳輸紀錄，比全量搬遷可控得多。
>
> 不採 C 的理由值得記下來，但措辭要準確：**跨區域拆分單一 CalculationRun 會顯著增加凍結集合原子性與確定性重演的實作及驗證成本，MVP 不接受該複雜度。**透過內容定址、不可變 manifest 與分散式協調，跨區域計算並非不可能做到；問題在於它的失敗模式與驗證成本遠超出 MVP 的合理範圍。若日後真的必須區域化，正確做法是 DEP-C（整個實例區域化），不是把單一計算切成兩半。
>
> **跨區域災備複寫不等於跨區域計算。**被動、加密、且受資料政策允許的備援複寫可以另行評估，它不影響 CalculationRun 的原子性——本 ADR 排除的是「計算過程跨區域」，不是「資料副本存在於另一區域」。
>
> #### 負面後果
>
> 中國母公司使用者的存取延遲；需確認客戶資安政策是否接受主資料存放於日本。
>
> #### 安全與法規影響
>
> DF-2 每次傳輸須記錄法律依據、DataController 組織、接收方範圍、保存期（NFR-DATA-001）。實際管理機構的認定是綜合判斷，資料存放地只是證據之一——不應以「資料放哪裡」單獨作為稅務結論的依據。
>
> #### 遷移與退出
>
> 區域變更等同資料遷移專案，須先完成 IF-12 全量導出並驗證控制總額。
>
> #### 重新檢討觸發條件
>
> ① 客戶或監管要求特定資料所在地；② 中國端延遲實測不可接受；③ 出現非中日的第三個司法管轄區客戶。
>
> #### 關聯
>
> §24.9 DF-1／DF-2、NFR-DATA-001、AC-DATA-001、INV-17

> ### ADR-03附件與證據包的物件儲存與 WORM
>
> **狀態**　\[PROPOSED\]　**影響**　M9、M10、NFR-INT-001、INV-26
>
> #### 背景
>
> 原始檔、附件與證據包必須不可覆寫且可驗證完整性（AC-ING-001、AC-INTG-001）。`DeliveryRecord` 與證據包另有保存期與 legal hold 要求（D-26-04、INV-26）。日本電子帳簿保存制度對電子取引資料另有保存與可視性要求——即使 MVP 只承擔轉換副本責任，副本的完整性仍須可證明。
>
> #### 候選方案與比較
>
> | 方案                             | 篡改防護 | 備註                                     |
> |----------------------------------|----------|------------------------------------------|
> | A 一般物件儲存＋應用層不可覆寫   | 應用層   | 擁有儲存憑證者仍可改寫；稽核說服力不足   |
> | **B 物件儲存＋版本控制＋物件鎖** | 儲存層   | 合規模式的保留期與 legal hold 有原生對應 |
> | C 專用歸檔服務                   | 儲存層   | 取用延遲高；適合超過保存期後的長期歸檔   |
>
> #### 目前建議
>
> **B。**NFR-INT-001 要求「在篡改測試中保持完整」，而應用層保證無法通過這個測試——測試的前提就是攻擊者具備應用層權限。物件鎖把保證下沉到儲存層，才是可測試的。
>
> #### 負面後果與風險
>
> **合規模式的保留期一旦設定即無法縮短。**誤設會造成儲存成本無法回收，以及與個資刪除請求的衝突。但反向的錯誤同樣嚴重——「預設從短」可能造成法定或契約要求的資料保存不足。因此正確的原則是：
>
> **保留期取依法令、契約及資料分類確認後的最低必要期間；未完成分類及批准前，不得套用不可縮短的 Compliance Mode。**
>
> | 資料類別                   | 處理                                   |
> |----------------------------|----------------------------------------|
> | 預覽產物                   | 短 TTL，治理模式                       |
> | 暫存上傳                   | 治理模式；完成分類後才轉入正式保存     |
> | 正式證據包與依法需保全資料 | 按**已批准**的政策進入 Compliance Mode |
>
> 設定介面必須在套用前顯示**預估到期日、容量與不可逆警告**。Legal hold 與一般 retention 分開管理，不共用同一組期限。
>
> #### 責任分工
>
> **R9 不應單獨決定法律保存期。**正確分工是：法務／資料控制法人／案件責任人**批准**保存政策；R9 Data Steward **執行、監控並提出變更**。
>
> #### 安全與法規影響
>
> legal hold 期間不得清除（INV-26）；正式資料到期刪除前必須支援退出導出（NFR-EXIT-001）。刪除本身要留痕——「已依政策刪除」和「不見了」在稽核上是兩件事。**刪除請求遇法定保存義務時，記錄拒絕或延期的法律依據，不直接解除物件鎖。**
>
> #### 遷移與退出
>
> IF-12 的導出必須包含附件索引與雜湊，使客戶在他處也能驗證完整性。
>
> #### 重新檢討觸發條件
>
> ① 平台角色由轉換副本改為正式保存載體；② 客戶要求自持金鑰（連動 ADR-06）；③ 出現超出物件鎖能力的保存要求。
>
> #### 關聯
>
> NFR-INT-001、AC-INTG-001、AC-ING-001、NFR-EXIT-001、INV-26、D-26-04

> ### ADR-04背景計算的執行與隔離方式
>
> **狀態**　\[PROPOSED\]　**影響**　M6、NFR-PERF-001、INV-17
>
> #### 背景
>
> CalculationRun 可能處理數十萬列並跨多個基礎與分層，執行時間不可預測。同時它必須是確定性的：同一凍結集合重跑得到相同結果（INV-17）。
>
> #### 候選方案與比較
>
> | 方案                         | API 延遲影響 | 獨立擴縮 | 備註                                           |
> |------------------------------|--------------|----------|------------------------------------------------|
> | A 同進程背景執行緒           | 有           | 否       | 長時間計算會排擠請求處理；無法針對計算單獨擴容 |
> | **B 獨立 worker 進程＋佇列** | 無           | 是       | 共用領域模型與資料存取層，不引入網路契約       |
> | C 每次計算啟動隔離容器       | 無           | 是       | 隔離最強但啟動成本高；對月次結帳頻率而言過重   |
>
> #### 目前建議
>
> **B 為預設，C 作為大型或高風險客戶的選項。**B 與 C 的差異只在部署配置，不影響工作器契約——這是把它們寫成同一個 ADR 的理由。
>
> #### 正面後果
>
> API 延遲與計算負載脫鉤；年結尖峰可單獨擴充工作器；工作器可先停機而不影響查閱。
>
> #### 負面後果與風險
>
> 需要處理冪等、重試、逾時後的狀態一致性。**重試不得產生第二個 run**——冪等鍵為 `calculation_run_id`，重複派工必須返回既有結果或安全地重算至相同結果。逾時後 run 必須進入 `FAILED` 並附人可讀原因，不得停在 `RUNNING`。
>
> #### 租戶公平性
>
> 佇列須設每租戶並行上限。年度結帳的尖峰可預期，不能讓一家客戶的年結卡住其他客戶的月結。OFFICIAL run 優先於 PREVIEW run，且優先序不由使用者調整。
>
> #### 確定性約束
>
> 工作器禁止讀取 wall-clock 與隨機來源，禁止查詢任何未凍結的「目前值」。任何為效能引入的快取必須以 `calculation_run_id` 為鍵，否則跨 run 的快取污染會製造無法重現的結果差異。
>
> #### 重新檢討觸發條件
>
> ① 單次計算時間超過 NFR-PERF-001 的門檻；② 出現需要硬隔離的客戶；③ 計算需要外部服務（例如 AI 建議）時，隔離要求會改變。
>
> #### 關聯
>
> NFR-PERF-001、AC-PERF-001、AC-RUL-001、INV-17、M6

> ### ADR-05～09延後決定的事項
>
> **狀態**　\[DEFERRED\]　共同原則：**先留抽象邊界，確保替換實作不改動領域模型。**
>
> | ADR    | 問題                         | 抽象邊界                                   | 解除延後的觸發條件                         |
> |--------|------------------------------|--------------------------------------------|--------------------------------------------|
> | ADR-05 | 資料庫分區策略               | 鍵已含 unit／period／run，可直接作分區鍵   | 單表資料量或查詢延遲超過門檻；先實測再決定 |
> | ADR-06 | 客戶自持金鑰實作             | `KeyProvider`                              | 客戶契約明確要求自持金鑰                   |
> | ADR-07 | append-only 稽核軌跡實作     | `ImmutableAuditStore`（無 update／delete） | 稽核軌跡量級或外部鑑證要求出現             |
> | ADR-08 | 規則引擎採 DSL、DMN 或程式碼 | `RuleEvaluator`，回傳恆為建議              | 規則數量或非工程人員自行維護規則的需求出現 |
> | ADR-09 | 具體雲端產品                 | —                                          | ADR-02 與 ADR-03 定案後                    |
>
> ADR-08 補充：MVP 以程式碼實作有限規則集是合理起點，但 `RuleVersion` 的計算式欄位**現在就不能假設語言**。一旦有人把 Java／TypeScript 片段直接存進去，日後改 DSL 就等於重寫全部規則。

## §28　畫面資訊架構與操作流程

### 28.1 三個表面與導覽分離

| 表面  | 名稱                   | 使用者                                     | 設計深度                                                   |
|-------|------------------------|--------------------------------------------|------------------------------------------------------------|
| \[A\] | 外部資料提供入口       | R1（日本會計人員、稅理士、其他來源提供者） | 極窄。只有上傳、看退件原因、補件、看自身提交狀態。日文優先 |
| \[B\] | Tenant 作業工作台      | R2／R3／R4／R5／R7                         | 主體。六個核心畫面到線框與狀態規格                         |
| \[C\] | Platform Control Plane | PlatformRuleCurator、平台維運              | 視覺可粗糙，**控制不可粗糙**。兩個關鍵畫面到線框           |

> **表面 C 不能和表面 B 混在同一側邊欄**
>
> 平台控制面必須有**獨立導覽、獨立角色、醒目的環境與權限標示**。更重要的是：**平台人員不應有一般的「切換成客戶」功能**——那會讓 ADR-01 的 RLS 隔離在人員操作層被合法繞過，而且事後無法區分「平台維運」與「查看客戶資料」。必要的支援存取一律走 break-glass：有期限、有理由、有批准、有醒目提示、全程留痕。

![](assets/fig-28-1.svg)

*圖 28-1　三個表面。A 與 B 的邊界是權限，B 與 C 的邊界是導覽與身分——後者若混用，RLS 的隔離會在人員操作層被合法繞過。*

### 28.2 表面 A：外部資料提供入口

| 畫面 | 名稱               | 入口 → 出口                   | 資料來源與對應                                                   |
|------|--------------------|-------------------------------|------------------------------------------------------------------|
| A-01 | 我的待提交         | 登入 → A-02／A-03             | M7 期間×法人指派、M3 缺漏清單。REQ-ING-001                       |
| A-02 | 上傳與補件         | A-01 → 驗證中 → A-03          | M3 `ingest()`。`provided_by`／`uploaded_by` 分別記錄。AC-ING-001 |

> **R1 看不到什麼，比看得到什麼更重要——但沒有路由不是安全邊界**
>
> 集團完整科目表、其他子公司資料、內部規則庫、母公司調整、未授權的審計資料，在表面 A **不存在對應的路由**，而不是「有路由但擋住」。擋住的東西遲早會因為某次權限設定錯誤而露出來；不存在的路由不會。
>
> **但「沒有路由」只降低誤曝面，不能代替後端授權與 RLS。**六層必須同時成立：

|-----|------------------------|------------------------------------------------------------|

| 2   | 沒有前端路由           | 手動輸入網址也到不了                                       |
| 3   | 不載入相關前端模組     | 表面 A 為獨立 route tree，最好是獨立前端入口或 BFF 範圍    |
| 4   | 不向瀏覽器預取相關資料 | 避免資料進了瀏覽器記憶體卻沒有渲染                         |
| 5   | **後端 API 仍須拒絕**  | 前四層都是便利性措施；這一層才是控制                       |
| 6   | **資料層仍受隔離**     | Tenant／ClientEngagement／ReportingUnit 三重範圍（ADR-01） |

#### B-00 規格　\[v1.1 新增・CR-002\]

> **B-00 與 B-01 不可互相替代**
>
> B-01 以**案件**為中心：進到某個客戶之後，這個客戶的期間走到哪。B-00 以**人**為中心：我手上有哪幾家、各卡在哪。一名職員同時負責五到六家客戶時，沒有 B-00 就必須逐一進入每個案件才能知道哪裡需要處理。
>
> **編號取 B-00 而非插入 B-01**——B-01～B-17 的編號在追蹤矩陣、決議紀錄與 §25 守衛對照中已被引用，重新編排會讓所有歷史引用同時失效。

| P0 範圍 | 內容 |
|---|---|
| 我正在處理的公司與期間 | 依 `EngagementAssignment` 過濾 |
| 等我處理的事項 | 待覆核／待批准／補證據／被退回／因粒度不足升級／**待身分確認**（`identity_status = PENDING_CONFIRMATION`） |
| 我的未完成草稿 | 依 `last_saved_at` 排序 |
| 一鍵回到上次編輯位置 | 客戶 × 法人 × 期間 × 工作物件 |

**延後至 P1**：截止日與逾期項目、背景匯入與計算的進度、容量與工作量分析。

> **強制顯示規則**
>
> **B-00 的每一列都必須同時顯示客戶、法人、期間與目前狀態**，且不因欄寬、摺疊或響應式版面而隱藏任一項。否則工作台雖然能跨客戶，反而增加誤入錯誤客戶的機會——這與 §24.1A 的歸屬完整性直接相關。

> **查詢必須遵守指派與權限**
>
> B-00 只顯示使用者**有權且被指派**的工作。未指派客戶的名稱、識別資訊、計數與匯總**皆不得出現**——包括「你的租戶還有 5 家未指派」這類看似無害的統計，那本身就是資訊洩漏。指派被撤銷後，該客戶即刻自 B-00 消失，且以既有連結直接存取其工作物件時一併被拒。

### B-05　調整編製、升級、覆核與批准

![](assets/fig-28-2.svg)

*圖 28-2　B-05 調整清單。三種阻擋（SOD-01、B 基礎缺漏、粒度不足）在同一畫面上以相同的視覺語法呈現：紅色⛔＋守衛編號＋原因＋可執行的下一步。*

> **「你不能覆核此筆」而不是把按鈕藏起來**
>
> SOD-01 被觸發時，按鈕不消失，而是顯示為不可用並附原因與下一步（指派給誰）。藏起來會讓使用者以為系統壞了或自己權限不足，然後去找管理員要權限——那正是控制被繞過的起點。**把控制講清楚，比把控制藏起來安全。**

#### 畫面提示 ≠ 違規嘗試

畫面在使用者按下之前就知道他不合格，這時顯示說明是**正常的引導**，不是控制事件。若把它記成 `ControlViolationAttempt`，稽核軌跡會被大量「使用者看了一下說明」的雜訊淹沒，真正的訊號反而消失。

| 情形                           | 寫入 ControlViolationAttempt | 說明                                           |
|--------------------------------|------------------------------|------------------------------------------------|
| 畫面預先判定不合格並顯示說明   | 否                           | 顯示原因、提供〔指派其他覆核人〕或〔請求指派〕 |
| 使用者繞過 UI 直接呼叫 API     | **是**                       | —                                              |
| 畫面資格已過期，送出時守衛拒絕 | **是**                       | 畫面載入後人員指派變動的競態                   |
| 重複嘗試已明確被拒絕的遷移     | **是**                       | 重複本身是訊號                                 |

**無障礙**：不使用完全無法聚焦的原生 `disabled` 按鈕，改用 `aria-disabled` 配明確說明，讓螢幕閱讀器使用者也能得知原因。但這只是前端表現——**後端 M7 在實際送出時仍必須重新裁決**，不得信任畫面的預先判定。

#### B-05 的組織方式：按「調整主題」分組，不按 BookBasis 分頁

同一項資產常常同時有 A→B 的稅務調整與 A→C 的準則調整，兩者在覆核時必須一起看。分頁會切斷這個關聯；單純的篩選也不足以呈現橋接關係。因此以 `subject_ref` 分組：

    調整主題：固定資產 FA-00125　機械装置
    ├─ A → B　LOCAL_TAX　　　　償却限度超過額　　　＋1,200,000
    ├─ A → C　GROUP_GAAP　　　耐用年数差異　　　　△  200,000
    └─ B → C　DEFERRED_TAX　　一時差異に係る税効果　＋  960,000

列表欄位至少包含：`from_basis`／`to_basis`、PostingLayer、規則類型、金額與幣別、狀態、證據成熟度、編製／覆核人、共同的 `subject_ref`。BookBasis、PostingLayer、規則類型與狀態皆為**可複選篩選器**；詳細側欄顯示三基礎的橋接關係。

> **措辭修正：發布不會讓任何 Tenant「停止執行」**
>
> v0.1 寫成「這次變更會讓 7 個 Tenant 的規則停止自動執行」是錯的——平台範本不會自動改寫 Tenant 已生效的規則版本（D-24-05），現行版本完全不受影響。正確的說法是**「7 個 Tenant 在採用此版本時將缺少必要粒度」**。這個差別很重要：前者聽起來像發布有立即破壞性，後者才是實情。

> **影響分析中的具名 Tenant 只能看到必要資訊**
>
> 若畫面顯示具名 Tenant，PlatformRuleCurator 只能看到**識別與涵蓋資訊**（Tenant 名稱、受影響科目範圍、粒度狀態），**不應看到客戶財務金額**。這是 ADR-01「平台控制面與租戶控制面分離」在畫面層的具體要求。

>
> `output_capability = NONE` 時，畫面必須提供**診斷資訊**——差在哪一列、差多少、來源是誰、哪個期間與幣別——但**不得提供任何看起來像財務報表的下載檔**，即使加了浮水印也不行。收到檔案的人不會每次都注意浮水印，而數字一旦離開系統就會被引用。

### 28.8 INSUFFICIENT_GRANULARITY 的畫面規格

> **這是最容易被做壞的一個**
>
> 「規則沒有執行」在畫面上很容易被表現成「這一項是零」或乾脆不顯示。使用者因此以為系統算過了、結果是沒有調整。這正是 UI-25-01 要求的核心：**系統沒有把結果當成零**，畫面必須說出來。

┌─ 升級處理 ── 粒度不足 ───────────────────────────────────────┐

│    期間：2026-01 ~ 2026-03                                     │
│    餘額：¥ 18,400,000                                          │
│                                                                │
│  ⚠ 本規則未執行。這不代表調整金額為零，而是無法計算。          │

| 元件           | 規格                                                                                                                             |
|----------------|----------------------------------------------------------------------------------------------------------------------------------|

| 控制例外橫幅   | 期間層級的黃色橫幅，出現在期間工作台、交付畫面與證據包預覽三處                                                                   |

| 環境與租戶標示 | 平台控制面全域紅色標示；break-glass 生效期間額外顯示倒數與理由                                                                   |

| 金額顯示       | 一律顯示幣別；雙幣並列時標明 `amount_role`（功能幣／報告幣），不以位置隱含                                                       |
| **EngagementContext** | 每個作業畫面**固定顯示**客戶、法人與期間；切換客戶時工作脈絡必須在視覺上可辨識；上傳、批准、正式輸出前再次顯示。**多分頁各自維持獨立的 context**，互不污染。**伺服器必須重新驗證物件與 Engagement 是否一致——不得依靠下拉選單保證資料歸屬**（§24.1A）\[v1.1・CR-002\] |

#### 離線未同步內容的暫存位置　\[v1.1 新增・CR-002\]

「保留本機內容」可以指三種完全不同的安全模型：分頁記憶體（關閉即失）、`sessionStorage`（分頁生命週期）、IndexedDB 等持久化瀏覽器儲存（**關閉瀏覽器後仍在，會在共用電腦上留下客戶財務資料**）。

**MVP 規則：離線未同步內容僅在目前分頁生命週期內暫存；關閉分頁前必須警告。持久化離線快取不屬 MVP。** 日後若啟用，須先納入 NFR-DATA-001 的涵蓋範圍並處理加密、登出時清除、保存期限與共用裝置風險。

若不明確擇一，就會出現「草稿已納入資料治理範圍，但瀏覽器本地草稿不在」的破口——這類破口不會出現在任何後端稽核報告裡。

### D-28-05　模擬鎖定（DRY_RUN）規格

直接重用 M7 的守衛評估器，不另建一套判斷邏輯——否則模擬結果與實際結果遲早會分歧。

    evaluateTransition(
      object = PeriodRevision,
      target = LOCKED,
      mode   = DRY_RUN
    )

| 與正式鎖定的差異             | 說明                                                                                  |
|------------------------------|---------------------------------------------------------------------------------------|
| 不改狀態                     | 期間仍停留在原狀態                                                                    |
| 不建立 Approval              | —                                                                                     |
| 不凍結版本                   | —                                                                                     |
| 不產生 CalculationRun        | **若尚無可用計算結果，只提示「CalculationRun 尚未完成」**，不得為了模擬而偷偷啟動計算 |
| 不寫 ControlViolationAttempt | 改寫一般的 `ControlPrecheckPerformed`                                                 |
| 正式送批時全部重新執行       | 模擬結果沒有任何預先核可的效力                                                        |

| 每項附加     | 負責角色、建議處理動作                                                                                         |
