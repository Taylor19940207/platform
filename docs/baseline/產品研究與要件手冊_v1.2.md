### v1.2 變更明細（CR-002・多案件日常作業模型）

手冊 v1.1 與設計書 v1.0 完整定義了**一個期間如何被正確處理**，但沒有定義**一個人如何同時處理多個期間**。事務所的實際工作方式是一名職員同時負責五到六家客戶，來回切換、做一半離開、隔天接續——這不是極端情境，而是這類產品最正常的使用方式。

**核心命題**：租戶隔離防的是「不該看到的人看到」，防不了「該看到的人放錯地方」。一名職員對其被指派的六家客戶都有合法權限，權限矩陣攔不住誤置——**這是兩種不同性質的控制，必須分開設計**。

|---|---|---|

### 文件治理原則

- 研究事實、產品決策、功能需求及未決問題分開標示。
- 只有會阻礙 MVP 的法規問題需要在開發前查到底；其餘進入研究待辦。
- 核心資料模型不綁定金蝶、Oracle 或 SAP；各 ERP 由輸出適配器處理。
- 本版本是 v1.1 產品基線；Part II 至 VII 為現階段產品承諾，Part VIII 是持續研究與變更出口。

下列定義適用於 Part II 至 VII。中文、日文或英文介面可以顯示不同名稱，但資料模型、需求、設計圖與驗收文件必須依本表理解；需要修改時由產品負責人與會計領域負責人共同批准。

| 詞彙 | 日文／英文對照 | 本手冊中的規範性定義 |
|---|---|---|
| 帳套 | 帳簿一式／ledger set | 某一法律實體或特定目的下相對完整的科目、期間、憑證、總帳、明細與報表資料集合。 |
| 法定帳 | 法定帳簿／statutory ledger | 依實體所在地法規與適用準則保存、申報或編製法定報表的正式帳務。 |
| 合併層 | 連結レイヤー／consolidation layer | 保存集團調整與抵銷分錄的報表層；不等同日本子公司的法定總帳或記帳憑證。 |
| 口徑 | 報告基準／reporting basis | 一組計量、分類、列報、匯率、期間及重要性政策所形成的報告視角，不只是幣別或語言格式。 |
| BookBasis | 帳簿基礎／measurement basis | 資料模型中的會計或稅務計量基礎。它可對應一套帳、調整層或計稅基礎，不必然是一套實體總帳。 |
| A 基礎 | 日本法定会計／Japan statutory | 日本子公司依日本適用會計政策形成的法定會計帳面價值。 |
| B 基礎 | 日本税務／Japan tax basis | 日本法人稅計算使用的計稅基礎及帳稅調節結果。 |
| C 基礎 | 中国集団 CAS／group CAS | 依中國企業會計準則及母公司集團政策形成的集團帳面價值。 |
| LOCAL_TAX | 税務調整 | A→B 的日本帳稅調整；服務日本稅務申告，不是集團準則調整。 |
| GROUP_GAAP | 集団会計基準調整 | A→C 的準則及集團政策調整。 |
| DEFERRED_TAX | 税効果調整 | 比較 C 與 B 所形成的合併口徑暫時性差異及增量稅效。 |
| CONSOLIDATION | 連結調整／消去 | 處理實體間往來、交易、投資與權益等合併抵銷及調整。 |
| 期間包 | 連結パッケージ／reporting package | 日本端按母公司指定期間、科目、維度、準則與模板交付的集團報告資料包。 |
| 證據包 | 監査証跡パッケージ／evidence package | 包含來源雜湊、映射與規則版本、計算、分錄、法源、附件索引及批准紀錄的可導出底稿。 |
| 轉換副本 | 変換用コピー／controlled conversion copy | 從正式來源取得、具完整性驗證及版本控制的副本；MVP 中不取代日本法定 system of record。 |
| 正式來源系統 | 正本システム／system of record | 對指定資料負有權威保存與正式紀錄責任的系統。 |
| 映射 | マッピング／mapping | 將來源科目、維度、關係人或現金流分類對應至集團標準的有版本規則。 |
| 調整 | 調整仕訳／adjustment | 在指定 BookBasis 或合併層改變金額、分類或列報的可追溯分錄或計算。 |
| 規則版本 | ルール版／rule version | 具有適用條件、生效期間、來源、計算與批准狀態的不可覆寫規則快照。 |
| 租戶／法律實體 | Tenant／LegalEntity | Tenant 是資料與權限隔離邊界；LegalEntity 是承擔法定權利義務並獨立報告的公司實體。 |
| 草稿／工作中資料 | 作業中データ／draft | 使用者尚未提交的編輯內容。**驗證未通過（借貸不平、證據未齊、映射未完成）仍必須可以保存**；草稿不是正式版本，也不得包裝成可入帳的財務輸出。 |
| 伺服器確認保存 | サーバ確定保存／server-confirmed save | 內容已寫入伺服器並回傳成功確認的狀態。**只有這個狀態才可以在介面上顯示「已保存」**；瀏覽器端暫存不算。 |

| identity_status | 同一性ステータス | 匯入批次的身分比對狀態，與處理進度狀態**正交**：NOT_CHECKED／MATCHED／PENDING_CONFIRMATION／MANUALLY_RESOLVED／CONFLICT。 |
| SourceIdentityResolution | 同一性人的確認記録 | 對 UNVERIFIABLE 批次的人工確認紀錄，**不可覆寫**，含確認者、時間、理由、證據與規則版本；效力只及該匯入批次版本。 |
| CalculationInputManifest | 計算入力マニフェスト | 建立計算執行時凍結的輸入清單，含不可變內容（或不可變引用）、`content_hash`、`hash_algorithm` 與 `canonicalization_version`。**重演比對的對象是這份凍結內容，不是目前的工作物件。** |
| object_version | オブジェクト版／concurrency version | 每次自動儲存即遞增，供併發控制使用。**不進入可稽核的版本鏈**。 |
| business_version | 業務版／business version | 提交、退回、覆核、批准等里程碑才產生的**可稽核正式版本**。一小時的編輯不會因為自動儲存而產生數百個版本。 |
| 凍結內容／目前工作物件 | 凍結内容／現行作業オブジェクト | 凍結內容是計算當時被固定下來的輸入；目前工作物件是草稿的最新狀態。**兩者不同屬正常情況**，不構成重演失敗；只有凍結內容遺失、損壞或雜湊不符才是失敗。 |

# PART I　產品研究報告

保留完整討論的問題背景、跨國帳務結構、準則轉換、人工作業、成本痛點與競品邊界，作為後續產品決策的證據基礎。

本篇產出：問題與市場空隙／中日作業與責任邊界／轉換流程及資料交付／競品與替代方案地圖。

## SECTION 01　核心結論

> 你們要解決的不是「再做一套 ERP」，而是建立日本當地法定帳與中國母公司集團帳之間，一條有法源、有版本、可追溯、可人工覆核，並可輸出至金蝶、Oracle、SAP 或其他母公司系統的跨境轉換橋樑。

- 日本子公司維持自己的日本法定帳、稅務申報與日圓報表；中國母公司則依中國企業會計準則及集團政策編製個別帳與合併報表。
- 日本報表不能只做語言與格式翻譯。真正工作包括科目映射、會計政策調整、會計期間統一、日圓轉人民幣，以及母子公司內部交易抵銷。
- 固定規則可以系統化，但收入、租賃、減值、準備、所得稅、特殊交易等事項仍需要專業人員判斷。
- 大型 EPM／合併系統的核心位於集團關帳與合併，雖可向前延伸至資料收集及映射，仍不直接提供日本法定帳轉中國集團口徑的全部專業判斷；其最低授權與導入門檻亦可能超出小型跨境團隊需求。
- 母公司的目的地系統可能是金蝶、Oracle、SAP、其他 ERP／合併系統或 Excel；產品核心應保持系統中立，再以適配器輸出。
- Oracle FCC、SAP Group Reporting、LucaNet 等位於合併與關帳市場；Oracle Accounting Hub 主要處理來源交易至分錄，屬相鄰產品而非主要直接競品。
- 國際會計事務所的優勢不只是客戶來源，而是真實案例、科目映射、準則差異、工作底稿與審核經驗；這些可以形成規則庫和產品護城河。

**研究範圍與重要提醒**　本文件依照完整對話整理，將重複內容合併，但保留所有實質觀點。內容是產品與流程研究，不構成針對個案的中國或日本法律、稅務、會計或審計意見。實際處理仍須依企業性質、適用準則、持股與控制關係、母公司系統版本、交易內容及申報年度確認。

## SECTION 02　什麼是帳套，以及跨國企業如何配置

帳套是會計系統內一套獨立、完整的財務帳目資料。通常包括會計科目、會計期間、憑證、總帳與明細帳、應收應付、財務報表、幣別、稅務設定及使用者權限。可以把它理解成一家公司在會計軟體中的獨立帳簿與資料庫。

### 跨國企業的一般架構

跨國企業通常不是全球共用一個帳套，而是採取「各法律實體獨立記帳 ＋ 集團統一標準 ＋ 期末合併報表」。一個公司法人通常至少有一個主要法定帳套；同一實體也可能在大型 ERP 內設置多個 ledger 或 book，以同時保存法定帳、集團帳、稅務帳與管理帳。

| 層級 | 用途 | 主要內容 |
|---|---|---|
| 當地法定帳套 | 當地記帳、報稅與法定報表 | 當地科目、幣別、稅制、會計準則及法定語言 |
| 集團管理帳 | 內部經營與績效分析 | 統一科目、成本中心、利潤中心、產品、地區與專案 |
| 集團合併層（非當地法定帳套） | 呈現整個集團的財務狀況 | 集團調整與抵銷分錄、外幣折算、商譽及少數股東權益；不構成日本法定總帳 |

### 集團統一維度

公司代碼／集團科目／成本中心與利潤中心／事業部、產品線、客戶與專案／關係人代碼。

其中關係人代碼尤其重要，否則集團內應收應付、收入成本、借款利息及未實現利潤很難自動核對與抵銷。

## SECTION 03　中國母公司與日本子公司的實際責任邊界

> 兩條合規線必須分開：日本子公司在日本完成法定記帳與稅務申報；中國母公司取得日本資料後，轉換為中國集團口徑，完成集團合併與中國端應履行的報告事項。

| 日本子公司／當地事務所 | 中國母公司／集團財務 |
|---|---|
| 日本法定帳簿與財務報表 | 建立中國集團科目與核算維度 |
| 日本法人稅、消費稅及其他當地申報 | 統一會計政策與會計期間 |
| 薪資、社保及地方稅務 | 日圓轉換成人民幣 |
| 日本當地審計或稅務調查配合 | 集團內部交易與投資抵銷 |
| 提供試算表、明細及支持文件 | 編製集團合併財務報表 |
| — | 處理中國端境外投資與所得報告事項 |

**合併財報不等於跨境合併納稅**　日本子公司作為獨立法人，原則上在日本申報並繳納日本稅款。中國母公司編製集團合併財務報表，並不等於把日本子公司全部會計利潤直接併入中國母公司的企業所得稅申報。股利、利息、服務費、特許權使用費、轉讓定價、預提稅、境外稅額抵免及受控外國企業等事項，仍須按照各自規定另行判斷。

## SECTION 04　從日本法定帳到中國集團帳的轉換流程

| 步驟 | 作業 | 成果 |
|---|---|---|
| 1 | 日本法定結帳 | 以日本法規、適用會計政策及日圓完成帳務與稅務資料 |
| 2 | 資料包準備 | 輸出試算平衡表、總帳、明細、合約、稅務與關係人資料 |
| 3 | 科目與維度映射 | 對應中國集團科目、部門、項目、客商及關係人代碼 |
| 4 | 準則與政策調整 | 將日本處理調整成中國準則及母公司集團政策口徑 |
| 5 | 期間統一 | 處理日本與中國結帳日或報告期間的差異 |
| 6 | 外幣折算 | 日圓折算成人民幣並辨認外幣報表折算差額 |
| 7 | 合併抵銷 | 抵銷投資、權益、內部往來、交易、利息、股利及未實現利潤 |
| 8 | 母公司系統輸出 | 生成金蝶、Oracle、SAP 或其他目的地可使用的憑證及報表包 |

### 第一層：科目及核算維度映射

| 日本帳科目示例 | 中國集團科目示例 | 補充資訊 |
|---|---|---|
| 普通預金 | 銀行存款 | 銀行、帳號、幣別 |
| 売掛金 | 應收帳款 | 客戶、關係人、帳齡 |
| 買掛金 | 應付帳款 | 供應商、關係人、帳齡 |
| 未払法人税等 | 應交稅費 | 稅種、所屬期間 |
| 資本金 | 實收資本 | 出資人、歷史匯率 |

映射不能只做一對一科目翻譯。同一日本科目可能需要依交易性質、客戶類型或部門拆分至不同集團科目；反之，多個日本科目也可能合併至一個集團科目。

### 第二層：會計政策與準則轉換

常見差異領域包括收入確認、固定資產與折舊、租賃、研發支出及無形資產、資產減值、準備與或有負債、員工福利、金融工具、所得稅、商譽及企業合併。具體是否存在差異及差異金額，不能只靠國別標籤判斷，必須回到交易與適用政策。

> **日本法定帳不回寫**：日本帳仍保留原處理；中國集團口徑的差異，通常以合併調整分錄或另編 reporting package 反映。

示例：如果某項設備在日本法定帳的年度折舊為 100 萬日圓，而依母公司統一政策計算為 80 萬日圓，則日本帳仍保留 100 萬日圓；集團報表包另作 20 萬日圓的調整。該差異也可能連動遞延所得稅，且需延續至未來期間。此數字僅為流程示例。

### 第三層：外幣折算

- 資產與負債項目通常採資產負債表日即期匯率。
- 收入與費用採交易發生日即期匯率，或以合理方法確定的近似匯率。
- 部分所有者權益項目涉及歷史匯率。
- 由此產生的外幣報表折算差額在權益相關項目反映。

### 第四層：集團合併抵銷

- 母公司長期股權投資與子公司所有者權益。
- 母子公司及子公司間的應收與應付。
- 集團內部銷售收入與採購或營業成本。
- 集團內部借款、利息及股利。
- 期末存貨、固定資產或無形資產中的內部未實現損益。
- 少數股東權益、商譽及相關後續計量。

## SECTION 05　為什麼必須保留人工審核

法源、準則及集團政策不同，只解決一部分問題。更大的難點是交易實質、估計與專業判斷。因此系統可以自動化已知規則，但不能合理地完全取代會計師、稅理士或集團財務的判斷。

| 處理層級 | 適合事項 | 控制方式 |
|---|---|---|
| 系統自動處理 | 固定科目映射、指定匯率、重複性分錄、格式轉換 | 規則版本、例外提示、批次核對 |
| 規則運算 ＋ 人工覆核 | 折舊差異、租賃計算、遞延所得稅、帳齡與減值提示 | 計算底稿、準備人與覆核人 |
| 專業個案判斷 | 收入、減值、訴訟、重組、併購、複雜關聯交易 | 合約與證據、判斷備忘錄、批准紀錄 |

### 常見人工審核項目

- **收入確認**：控制權何時移轉；是否有退貨、折扣、代理或多項履約義務。
- **租賃**：合約是否包含租賃、租期、續租選擇與折現率。
- **固定資產**：資本化或費用化、折舊年限、殘值及減值跡象。
- **研發與無形資產**：支出性質及何時符合資本化條件。
- **資產減值**：現金產生單位、未來現金流、折現率及可收回金額。
- **準備與或有負債**：訴訟、保固、退休給付等是否及如何認列。
- **所得稅**：會計與稅法差異、遞延所得稅、境外稅額抵免。
- **關聯交易**：是否屬集團內交易、是否需抵銷及轉讓定價風險。
- **特殊交易**：企業合併、重組、政府補助及股權交易。

資料充分性同樣是難點。如果日本端只提供損益表中的「外包費」，中國端可能無法判斷其中是否包含應資本化的系統開發支出。因此財務報表必須搭配總帳、明細、合約、發票、計算表及會計判斷說明。

## SECTION 06　日本端應交付的集團報表包

只有日本格式的資產負債表與損益表，通常不足以完成中國合併。母公司最好制定固定的 reporting package，按月、季或年提交。

| 最低交付內容 | 目的 |
|---|---|
| 完整試算平衡表及總帳 | 確認帳務完整性並追溯至分錄 |
| 重要科目與異常交易明細 | 辨認需人工判斷的交易 |
| 日本科目與集團科目對照表 | 持續執行科目及維度映射 |
| 固定資產、折舊及無形資產明細 | 計算折舊、攤銷及準則差異 |
| 應收與應付帳齡 | 減值評估及往來核對 |
| 關係人交易及期末餘額 | 完成集團內對帳與抵銷 |
| 借款、利息、擔保與承諾明細 | 處理金融項目、利息及披露 |
| 所得稅與遞延所得稅資料 | 辨認稅會差異與遞延稅影響 |
| 股東權益變動與股利資料 | 處理投資抵銷、權益及股利 |
| 現金流量分類資料 | 編製集團現金流量表 |
| 與母公司會計政策不一致事項清單 | 集中管理準則與政策調整 |
| 日本法定帳至中國集團帳調節表 | 解釋兩種口徑的差額 |
| 支持合約、發票、計算表與判斷備忘錄 | 支持專業判斷與稽核追溯 |

### 每筆調整的工作底稿欄位

差異事項與交易背景／日本法定帳處理／中國準則及集團處理／調整金額與借貸分錄／法源、集團政策與判斷依據／支持文件／準備人、覆核人與批准時間／是否為每期重複或未來轉回項目。

## SECTION 07　關鍵會計、稅務與審計發現

### 現金流量表的資料粒度

中國企業會計準則以直接法列報經營活動現金流量，並補充提供將淨利潤調節為經營活動現金流量的資料；日本準則允許直接法與間接法。產品不能只收一張日本間接法現金流量表，而應取得足以重建母公司直接法口徑的收付款分類、往來變動、非現金交易及關係人現金流資料。

資料粒度由母公司管理層依編製方法與重要性決定，再與外部審計師事前溝通其可審計性與證據需求；確認結果應保存為客戶專屬規則，避免審計時才發現粒度不足。

### 會計期間不一致是架構決策

中國會計年度為公曆 1 月 1 日至 12 月 31 日，日本子公司則可能採 4 月至翌年 3 月。CAS 33 允許按照母公司期間調整子公司報表，或要求子公司按母公司期間另行編報；修改日本公司的法定事業年度只是企業治理選擇，不是唯一會計選項。系統必須支持按月抽取、跨法定年度組合、期初期末銜接及比較期間。

### 首次轉換與期初餘額

第一次導入不能只從當期調整開始。既有日本子公司通常需要建立集團口徑期初餘額、累積準則差異、歷史匯率、投資與權益資料，以及比較期間處理。是否追溯重編取決於新設、收購、同一控制、非同一控制、政策變更或單純更換工具等具體情況。首次導入工作量應由事務所既有案件工時驗證，不能先假設固定倍數。

### 多基礎會計模型

研究確認系統必須分開日本法定會計、日本稅務計稅基礎及中國集團 CAS，並以 LOCAL_TAX、GROUP_GAAP、DEFERRED_TAX、CONSOLIDATION 四類規則處理。完整定義、數值示例及遞延所得稅邏輯以 Part IV §14 為唯一權威來源，本節不重複維護。

### 跨境稅務與資料保存風險

- 集團內服務、代墊及系統費需要移轉定價、受益測試、成本分攤與契約證據；獨立第三方事務所按正常價格收費不是同一風險。
- 中國實際管理機構認定須綜合管理場所、財務與人事決策、帳簿印章及董事高管居住等條件；資料存放地是證據之一，不是單獨決定因素。
- 日本帳簿書類通常保存 7 年，特定欠損年度可能為 10 年；電子交易資料應按電子帳簿保存制度保存。伺服器不必物理位於日本，但日本保存場所須能迅速顯示及輸出。
- 產品必須先決定是正式法定保存載體、轉換副本或混合模式，不同模式承擔不同合規責任。

### 審計可接受性是產品需求

若平台構成客戶財務報告資訊系統的一部分，中國註冊會計師審計準則第 1241 號要求審計師考量服務機構及其控制。平台因此需要原始資料留存、版本、批准、證據附件、可重演計算及不可任意竄改的軌跡。長期可研究服務機構控制鑑證，但不應承諾審計師不再索取任何資料。

## SECTION 08　跨境報告工作的成本結構

成本論證必須分開三個層次，不能把母公司人工作業費誤寫成 Oracle 授權費，也不能把不同範圍的事務所報價當成單一市場價。

### 第一層：日本端專業服務

日本市場已將「連結パッケージ作成」視為可獨立報價的服務。可查得的公開起始報價案例包括中島國際稅務會計事務所每次 20 萬日圓、日本橋國際會計事務所 50 萬日圓起、リライル會計事務所 75 萬日圓起。三者的工作範圍、頻率、準則轉換深度及客戶規模不同，因此只能證明獨立計價與價格離散，不能推出統一市場價。

### 第二層：母公司端內部處理

對話中的既有案件提到母公司端每年約 200 萬至 300 萬日圓的處理成本。這是待以客戶訪談核實的內部案例資料，需補充人數、工時、報告頻率、幣別、包含流程及計算期間；在完成基線前，不把它當作軟體價格或一般市場平均。

### 第三層：大型系統的結構性門檻

Oracle 公開牌價顯示，EPM Standard 每位命名使用者每月 250 美元、最低 10 人，牌價最低約 3 萬美元／年；EPM Enterprise 每位每月 500 美元、最低 25 人，牌價最低約 15 萬美元／年。標準訂閱期通常為三年，因此三年牌價承諾約為 9 萬與 45 萬美元，尚未包含折扣、稅金、匯率、導入、整合及顧問費。對只有 3 至 5 名財務人員參與合併的團隊，最低用戶數與合約年期形成結構性門檻。

大型 EPM／合併工具的核心價值位於集團關帳與合併，雖可向前涵蓋資料收集、映射及部分調整，仍通常需要顧問配置與專業人員判斷 local statutory → group GAAP 的具體差異。

> 市場空隙不是單純「更便宜」，而是把已被獨立計價、但尚未標準化的跨境 reporting package 工作，做成比 Excel 更可控、又不要求企業承擔大型 EPM 最低席次與導入成本的產品。

## SECTION 09　產品研究結論：跨境財務資料對齊與系統銜接

從產品角度看，這不是只為目前幾個客戶解決作業問題，也不應被定義為單一的金蝶轉換工具。更普遍的需求是：母公司、海外子公司、兩地會計事務所及兩套財務系統彼此不同，但在集團結帳時，海外資料必須轉成母公司的統一口徑。

母公司可能使用金蝶、Oracle、SAP、其他 ERP、專業合併報表系統，甚至以 Excel 收集海外資料；海外子公司則可能使用當地會計軟體，並由另一家當地會計或財稅事務所負責。即使母子公司由同一家國際會計事務所服務，兩地團隊、系統、法規與工作底稿仍可能不同。

> **建議定位**：連接海外子公司的當地合規帳與母公司的既有財務系統，自動處理可規則化的科目、準則、幣別及格式轉換，並將需要專業判斷的部分交由會計人員審核。

### 產品成立的四種不一致

| 不一致來源 | 具體問題 |
|---|---|
| 系統不同 | 母公司與子公司使用不同 ERP、會計軟體或報表工具 |
| 資料不同 | 科目、維度、編碼、檔案格式及資料粒度不一致 |
| 規則不同 | 會計準則、稅法、幣別、會計期間及集團政策不一致 |
| 組織不同 | 母公司、子公司及兩地事務所之間責任與工作底稿分散 |

### 不同服務安排下都存在需求

| 服務安排 | 產品價值 |
|---|---|
| 同一家國際會計事務所 | 統一跨國團隊格式、規則、審核紀錄與交付流程 |
| 兩地由不同事務所負責 | 建立中立協作層，明確資料、責任、修改與批准紀錄 |
| 母公司自建財務團隊，海外外包 | 當地事務所提交資料，母公司在系統內覆核並接入既有 ERP |

### 不取代的部分

- 不取代日本既有會計軟體的日常記帳、發票、薪資、庫存與稅務申報。
- 不取代母公司的金蝶、Oracle、SAP、其他帳套、集團控制及當地申報流程。
- 不宣稱 AI 或規則引擎可以自動保證中日合規。

### 核心輸出

中國集團科目口徑的試算表／中國準則及母公司政策調整分錄／日圓與人民幣雙幣資料及折算差額／母子公司往來與關係人交易明細／現金流量分類與核算維度／母公司系統可接受的 Excel、CSV、憑證、API 資料或報表包／日本法定帳至中國集團帳的調節表／每筆調整的法源、工作底稿、版本與批准紀錄。

### 建議系統模組

| 模組 | 主要功能 |
|---|---|
| 資料匯入層 | 匯入日本試算表、總帳、明細及支持文件；保留原始檔案雜湊與版本 |
| 映射層 | 科目、部門、項目、客商、幣別及關係人映射；支持一對多與條件式映射 |

## SECTION 10　競品、替代方案與相鄰產品

競品不能只用品牌平面比較，而應按所解決的工作層次分組。本產品真正要取代的，首先是「Excel＋日本事務所＋母公司財務」的人工協作；直接參照組是合併與關帳產品及跨國合規服務。Oracle Accounting Hub 主要解決大量業務交易轉為可稽核分錄，屬相鄰產品，不是最直接的 local statutory → group GAAP 對手。

### Oracle Cloud EPM Financial Consolidation and Close

Financial Consolidation and Close，簡稱 FCC，主要負責集團合併與關帳。它收集各子公司資料，執行外幣換算、關係人與內部交易抵銷、投資及權益抵銷、調整分錄、合併報表、關帳工作流及稽核紀錄。它的前提通常是各子公司資料已經整理成集團可接受的口徑。

| 環節 | 實際內容 |
|---|---|
| 輸入 | 各國子公司的試算表、集團科目餘額、關係人資料、持股資料、匯率及調整資料 |
| 處理 | 把所有子公司加總，再做外幣折算、應收應付及收入成本抵銷、投資與權益抵銷、少數股東權益、商譽及合併調整 |
| 流程管理 | 控制哪些子公司已提交、誰覆核、哪些差異未解決、關帳目前進行到哪一步 |
| 輸出 | 集團合併資產負債表、合併損益表、合併現金流量表、附註資料及管理報表 |
| 不主要負責 | 日本日常記帳、日本稅務申報，以及逐筆判斷日本帳應如何轉為中國準則 |

> 簡單說：FCC 是把已經整理好的各國子公司數字，合併成整個集團的一份財務報表。

| 與本產品的關係 | 判斷 |

| 重疊功能 | 匯率折算、調整分錄、集團內交易核對、審核流程及稽核紀錄 |
| 不同核心 | FCC 重點是集團最終合併；本產品重點是日本當地帳至母公司口徑的前置轉換 |
| 競合定位 | 重疊程度低至中，主要屬下游互補；可輸出 Oracle FCC reporting package |

### Oracle Fusion Accounting Hub

Accounting Hub 是 subledger accounting 平台。它主要接收保單、支付、銀行流水、訂單等外部業務系統交易與參照資料，套用會計規則後產生標準化、可追溯的會計分錄；也能接收總帳餘額，但核心流程仍是「交易 → 分錄」。它與本產品在規則、映射及追溯上相鄰，問題起點卻不同。

| 環節 | 實際內容 |
|---|---|
| 輸入 | 不同 ERP、保單、銀行、支付、銷售或其他業務系統產生的交易與參照資料 |
| 處理 | 依來源交易與中央會計規則決定借貸科目、金額、帳簿及核算維度 |
| 分錄生成 | 依規則產生標準化會計分錄，保存來源交易、規則版本、計算過程及修改紀錄 |
| 輸出 | 可進入總帳、報表、分析或下游合併系統的統一會計資料與可稽核分錄 |
| 不會自動知道 | 客戶特定的中日準則差異、交易實質及專業判斷；這些通常仍需顧問或會計人員配置與覆核 |

> 簡單說：Accounting Hub 主要把業務交易變成分錄；本產品主要把已形成的日本當地帳，轉成母公司集團口徑。

| 與本產品的關係 | 判斷 |
|---|---|
| 重疊功能 | 多來源匯入、科目映射、規則、分錄、核對及稽核軌跡 |
| Oracle 優勢 | 全球企業平台、大量交易處理、多帳簿及與 Oracle 生態整合 |

**資料接受角色**（CR-002 新增）：匯入批次的身分比對結果為 `UNVERIFIABLE` 時，只有跨境編製人或客戶政策指定的資料接受角色可以人工確認。**上傳者不得確認自己上傳的批次**——此為實例級控制（`resolved_by ≠ uploaded_by`），不取決於他當下切換成哪個角色；同一自然人同時具有記帳人員與編製人身分時，角色級禁令擋不住，必須由另一自然人確認。

基本設計書 §24 在本表基礎上補齊三個治理角色（客戶管理者／顧問、規則管理員、資料治理員），並將職責分離拆為角色級硬禁與實例級控制兩層；上述資料接受角色的實例級條件在設計層編為 SOD-07。本手冊維持原六角色作為需求層定義，設計層的九角色模型以基本設計書為準。

### 輸入與交付資料要求

- **最低輸入**：試算表、總帳或必要明細、科目表、期間、幣別、關係人標識、固定資產明細、稅務基礎或申告調整、支持文件及母公司政策。
- **粒度與涵蓋範圍**（CR-001 新增）：每一次匯入須記錄資料粒度（BALANCE／JOURNAL／SUBLEDGER／DOCUMENT）與涵蓋範圍（科目範圍 × 期間 × 完整度）。TB 為每期必要；GL 明細為必要，但可依科目、交易類型與重要性協商範圍，重要科目與異常交易必須有明細。
- **粒度不足的後果**（CR-001 新增）：規則所需粒度高於實際涵蓋粒度時，該規則不得自動執行，須建立調整並升級人工判斷，並記錄升級原因、受影響科目範圍與處理選項。**不得把「規則沒有運行」呈現為「結果為零」。**
- **宣告目標與身分比對**（CR-002 新增）：每一次匯入必須先宣告目標客戶、法人與期間，系統再比對檔案內容與該宣告，產生 MATCH／CONFLICT／UNVERIFIABLE 三值結果。**`CONFLICT` 硬性阻止接受且不提供人工豁免**；`UNVERIFIABLE` 須由資料接受角色人工確認並記錄理由，效力只及該批次版本。
- **工作中資料的保存**（CR-002 新增）：系統不得因為資料尚未完整而拒絕保存，但可以阻止它提交、批准、計算或輸出。離線未同步內容僅在目前分頁生命週期內暫存，**不得寫入持久化瀏覽器儲存**（共用電腦風險）。
- **輸出**：集團科目試算表、四類調整分錄、雙幣資料、關係人明細、現金流分類、調節表、母公司匯入檔及審計證據包。
- 資料不足不得靜默估算；系統應標記缺漏、影響、負責人、截止日及解除條件。
- **P0 現金流**：母公司管理層確認方法與粒度，系統保存該規則並收集、映射、輸出支持資料；P1 才提供直接法自動重建與勾稽。
- 會計期間不同時，支持按月組合、母公司期間調整或另行編報；治理上變更事業年度另作決策。

資料模型先把會計基礎、稅務基礎與集團基礎分開，避免工程上把不同目的的調整混成同一套分錄。

## SECTION 14　三基礎、兩橋樑與四類規則

| 代號／規則 | 比較或處理 | 記錄位置與目的 |
|---|---|---|
| A｜日本法定會計 | 日本 GAAP 帳面價值 | 日本子公司法定總帳及報表 |
| B｜日本稅務 | 日本計稅基礎 | 法人稅申告及帳稅調節 |
| C｜中國集團 CAS | 母公司集團帳面價值 | 合併報表及集團政策 |
| LOCAL_TAX | A → B | 日本稅務調整；不是集團準則調整 |
| GROUP_GAAP | A → C | 日本法定帳轉中國集團口徑 |
| DEFERRED_TAX | C ↔ B | 合併口徑暫時性差異及增量稅效 |
| CONSOLIDATION | 實體間／投資關係 | 合併調整與抵銷分錄，不屬日本法定記帳憑證 |

> 同一資產可同時產生 A→B 的日本稅務調整與 A→C 的集團準則調整，但那是兩條不同橋樑，不是同一調整做兩次。遞延所得稅最終比較 C 與 B。

例：A＝90、B＝85、C＝92。日本帳稅差異為 5，集團準則調整為 2，最終 C 與 B 的暫時性差異為 7。若日本帳已就 5 認列遞延所得稅，集團層只補增量影響。稅率應採預計轉回期間適用的已制定稅率；並判斷可抵扣差異的可實現性。

# PART V　系統架構

核心是一個與 ERP 解耦的跨境轉換引擎；金蝶、Oracle、SAP 與 Excel 只是輸入或輸出的適配器。

本篇產出：六層邏輯架構／核心與適配器邊界／安全、隔離與可重演性／法定保存模式與 ADR。

## SECTION 16　邏輯架構與元件邊界

| 層 | 責任 |
|---|---|
| 1｜匯入與適配 | Excel／CSV、TB、總帳、資產、稅務與附件；格式驗證、雜湊、版本、來源列 ID 及**資料粒度與涵蓋範圍記錄** |
| 2｜標準資料模型 | 統一科目、維度、實體、期間、基礎、幣別與關係人，不含客戶 ERP 特有邏輯 |
| 3｜多基礎與規則引擎 | 保存 A／B／C 等基礎，執行四類規則、調整、轉回及期初延續 |
| 4｜人工工作流 | 例外、評論、附件、準備－覆核－批准、鎖定與重新開啟 |
| 5｜折算與核對 | 匯率版本、試算平衡、關係人核對、現金流與差異提示 |
| 6｜輸出適配 | 可配置 Excel／CSV、金蝶模板、證據包；後續 Oracle／SAP／API |

### 關鍵架構原則

- 轉換核心不得依賴某一金蝶版本；適配器只處理欄位、格式、維度與傳輸。
- 規則版本與資料版本一起鎖定；同一輸入與同一版本重跑必須得到相同結果。
- 自動規則只產生建議或依授權直接過帳；重大或例外項強制人工覆核。
- **規則所需資料粒度高於實際涵蓋粒度時，該規則不得自動執行**（CR-001 新增）。
- **草稿在伺服器端持久化**；瀏覽器端暫存只服務離線期間，不得成為唯一保存位置（CR-002 新增）。
- **檔案取得伺服器接收確認後，其驗證、解析、匯入與背景計算不因瀏覽器關閉或 Session 到期而中止**；尚未完成傳輸者支援分段續傳，完整雜湊驗證前不得標記為已上傳（CR-002 新增）。
- **版本語意分三層**：併發控制版本（每次自動儲存遞增）、可稽核業務版本（里程碑才產生）、計算輸入凍結清單（建立計算執行時固定內容與雜湊）。**計算的可重演性由凍結清單保證，不得只記一個內容會變動的識別碼**（CR-002 新增）。
- 每個租戶資料、金鑰、權限與匯出範圍隔離；管理員行為同樣留下稽核紀錄。
- **租戶隔離不等於歸屬完整性**：隔離防的是越權存取，防不了有權者把資料放到錯誤客戶下；歸屬正確性須由伺服器端重新驗證，不得依靠介面選單（CR-002 新增）。
- 第一階段以可配置檔案交換降低整合風險；資料契約穩定後再建 API。
- 多語能力是核心架構：UI 翻譯、主檔多語名稱及使用者內容／翻譯版本分層，日期與字元正規化不破壞原始值。

### 法定保存角色的三種模式

| 模式 | 平台角色 | 主要設計影響 |
|---|---|---|
| 正式保存載體 | 平台承擔法定帳簿／電子交易資料保存 | 需完整對應日本保存、可視性、真實性、期限與檢查要求 |
| 轉換副本 | 正式資料仍在日本既有系統，平台保存受控副本與轉換證據 | 依產品章程作為 MVP 預設；須能指出正式來源並驗證副本完整性 |
| 混合模式 | 部分原件在原系統，部分證據或電子交易資料在平台 | 需逐類資料建立保存責任矩陣與導出程序 |

### 測試資料與環境策略

- 開發及一般測試環境不得使用未經批准、未處理的真實客戶資料；先建立可版本化的中日標準合成資料集。
- 匿名化不只遮罩公司名稱，還要處理交易對手、帳號、地址、自由文字、附件及稀有交易的再識別風險。
- 合成或匿名資料必須保持借貸平衡、期間銜接、A／B／C 差異、遞延稅、匯率及關係人對帳等核心會計關係。
- 若性能或缺陷重現必須使用真實資料，需案件負責人與資料管理者批准，置於隔離環境並限制人員、用途、保存期與導出。

### 待決架構決策紀錄（ADR）

- 租戶隔離方式、部署區域、資料加密與客戶自持金鑰需求。
- 規則引擎採聲明式配置或程式外掛，以及計算沙箱與回溯重算策略。
- 附件與大型總帳的保存層、雜湊、不可竄改性及長期歸檔。
- 金蝶確切產品、版本、模組、匯入 API 與核算維度限制。

### 資料粒度與規則執行（CR-001 新增）

匯入模組須記錄每一資料集的粒度（BALANCE／JOURNAL／SUBLEDGER／DOCUMENT）與涵蓋範圍（科目範圍 × 期間 × 完整度）。當某條規則所需粒度高於該範圍的實際涵蓋粒度時：

- 該規則不得自動執行；
- 系統須建立或更新一筆調整並升級為人工判斷，記錄規則、所需粒度、實際粒度、受影響科目範圍與涵蓋紀錄；
- 使用者可選擇補提供明細、改為人工判斷或本期停用該規則，三者皆須留下理由；
- 證據包須揭露該科目範圍的實際追溯等級。

**不得把「規則沒有運行」呈現為「結果為零」。**

### 多案件日常作業模型（CR-002 新增）

一名職員同時負責五到六家客戶並在其間切換，是這類產品最正常的使用方式。本節定義該情境下的四項要求。

**一、草稿持久化。** 可建立、保存、離開、恢復及廢棄草稿；**驗證未通過仍可保存**——借貸不平、證據未齊、映射未完成皆不得成為拒絕保存的理由。介面須顯示儲存狀態與最後成功保存時間，離開頁面時若仍有未保存內容必須警告。

| 情形 | 行為 |
|---|---|
| 連線正常、內容處於變更中 | 任一已輸入內容自產生起 **W 秒內須取得伺服器確認保存**（W 為 MVP 暫定 5 秒，可經批准放寬至 10 秒） |
| 逾 W 秒未取得確認 | 介面轉為「尚未保存／儲存延遲」，**不得維持「已保存」** |
| 離線或伺服器無回應 | 顯示「未同步／離線」；W 不適用；恢復連線後重新同步 |
| 離線未同步內容的位置 | **僅在目前分頁生命週期內暫存**；持久化離線瀏覽器快取不屬 MVP |

**二、草稿清理的排除條件。** 不得簡單規定「N 年後自動刪除」。下列五種情形必須排除於自動清理之外：已納入已鎖定期間的版本、與正式調整存在版本鏈的草稿、受 Legal hold 涵蓋者、尚未結案的案件、正在爭議或審計中的資料。長期未動者先標記為過期，由有權角色批次清理，**真正刪除仍依 NFR-DATA-001 的分類與保存政策**。

**三、併發編輯與 Session。** 不鎖整個期間，否則兩個人無法同時處理不同調整。以工作物件為併發粒度，每次保存帶併發控制版本；版本不符時不得由最後寫入者直接覆蓋，須顯示誰在何時改了哪一版並提供比較、重新載入或另存的選擇。**同一個人開兩個分頁，視為兩個不同的編輯來源**；同一編輯來源的連續自動儲存不得觸發衝突畫面。Session 到期後先重新驗證身分再返回原畫面，已在背景執行的匯入或計算不因此中止。

**四、版本語意與計算重演。** 自動儲存只遞增併發控制版本，不產生可稽核的正式版本——否則一小時的編輯會製造數百個版本節點。建立計算執行時，須以**計算輸入凍結清單**固定其納入的每一筆輸入內容與雜湊；計算開始後的草稿修改不改變既有執行的凍結清單。

> **重演的比較對象**
>
> 重演時必須取得凍結清單所保存或引用的**不可變凍結內容**並重新計算其雜湊。凍結內容遺失、損壞或雜湊不符時視為重演失敗，**不得改讀目前工作物件並宣稱重演一致**。
>
> **目前工作物件與凍結清單不同屬正常情況，不構成重演失敗**——草稿本來就會繼續前進。凍結清單另須保存雜湊演算法與標準化版本，否則日後序列化方式一改，內容相同也會算出不同雜湊。

### 匯入身分一致性比對（CR-002 新增）

租戶隔離防不了誤置：一名職員對其被指派的六家客戶都有合法權限，把 A 公司的檔案上傳到 B 公司時，權限矩陣不會攔阻。因此匯入必須先宣告目標，再比對檔案內容。

| 判定 | 意義 | 處理 |
|---|---|---|
| MATCH | 內容與宣告目標一致 | 可繼續 |
| **CONFLICT** | 明確法人代碼或期間不一致 | **硬性阻止接受，不提供人工豁免**。只能修正宣告目標、重新上傳正確檔案，或以新版識別規則重新偵測 |
| UNVERIFIABLE | 檔案缺少可靠識別資訊 | 由資料接受角色人工確認，**須記錄理由與證據**；效力只及該批次版本 |

判定不得由單一相似度分數決定。證據強度分三級：**權威識別符**（法人番号、統一編號、契約內法人代碼、期間代碼）是唯一可以產生 `CONFLICT` 的等級；**公司名稱加上已批准別名表**可作為 `MATCH` 的證據；**僅模糊名稱相似則維持 `UNVERIFIABLE`**，不得升為 MATCH，也不得降為 CONFLICT。

> **兩個不能犯的錯**
>
> 不能把 UNVERIFIABLE 當成 MATCH——那等於沒有控制。也不應因為公司名稱少一個「株式会社」就直接封鎖——那會讓使用者學會忽略警告。

身分比對狀態與匯入批次的處理進度狀態**正交**，不併入主狀態機。批次可以正常走完格式驗證流程，但在身分狀態轉為「已比對相符」或「已人工確認」之前**不得被接受**。已接受的批次日後若經人工或影響分析觸發重新評估而得到 `CONFLICT`，既有紀錄不原地改寫（歷史事實必須保存），而是建立影響評估、標記受影響的期間修訂與計算執行，交由覆核與批准角色決定重開、更正或當期反映。**規則升版本身不自動重評估歷史批次。**

### 首次轉換專用流程

- 判定導入性質：新設、收購、同一／非同一控制、政策變更或更換工具。
- 收集最早必要日期的 A、B、C 基礎及歷史匯率，建立期初與累積調整。
- 決定比較期間是否追溯重編，並保存管理層政策及審計溝通紀錄。
- 把一次性建立分錄與日後重複規則分開，完成期初至當期期末橋接。

### 人工判斷與例外狀態

每個自動結果可處於：建議、待證據、待編製、待覆核、退回、已批准、已鎖定、已替代。手工覆寫不得刪除原建議，需保留前後數值、理由、附件及批准。規則無法確定時應升級人工，不得為了自動化率而猜測。

**AC-CTX-001　跨客戶操作防誤用**

| 子案例 | Given／When／Then |

| CTX-e | 確認的版本效力。When 上傳同一檔案的新版本或重新解析產生新評估；Then 須重新確認，原確認不自動沿用，兩筆紀錄並存且皆不可覆寫 |

| CTX-g | 正交狀態軸。Given 身分狀態為待人工確認的批次；When 其處理進度走完格式驗證；Then 進度可推進但**不得被接受**，直到身分狀態轉為已人工確認 |
| CTX-h | 歷史重評估產生影響評估。Given 已接受批次經人工觸發重評估得到 CONFLICT；Then 原紀錄不被原地改寫，建立影響評估並標記受影響的期間修訂與計算執行，交由覆核與批准角色處理 |
| CTX-i | 規則升版不自動重評估。When 未經人工或影響分析觸發；Then 歷史批次身分狀態不變，亦不產生影響評估 |

### 審計與現金流驗收

- 外部審計師可從輸出數字反查來源並重演抽樣調整，無需平台外重新建立同一份轉換底稿；**反查深度以該科目範圍的實際追溯等級為限，不得超過實際 DataCoverage**。不代表審計師不得索取其他資料。
- 證據包可按實體、期間、調整類型、編製人與重要性篩選及完整導出。
- **草稿導出與正式輸出分屬兩條路徑**，不得混同；草稿導出不構成可入帳的財務輸出（CR-002 新增）。
- 母公司已書面確認現金流方法與粒度，並保存與審計師溝通紀錄；測試資料可重建要求的現金流分類。

# PART VIII　法規與規則持續補充

法規研究不應無限延伸。先完成會阻塞資料模型、控制或 MVP 的問題；其餘進入有版本、有責任人的研究待辦。

本篇產出：規則分層與生命週期／研究登錄簿／風險與客戶訪談／後續研究待辦與決策摘要。

## SECTION 21　規則治理與生命週期

「把法源法規做好」不是建立法規文字庫，而是分開日本強制法規與稅務、中國企業會計準則、母公司集團政策及客戶專屬設定，並把能執行的部分轉為有版本的規則。

| 規則層 | 內容 | 主要責任人 |
|---|---|---|
| 日本法定／稅務 | 日本記帳、申告、帳稅調節與保存 | 日本稅理士／會計專業人員 |
| 中國 CAS | 境外子公司轉成母公司集團口徑 | 中國集團會計／審計專業人員 |
| 集團政策 | 折舊、重要性、匯率、期間、現金流與管理層判斷 | 母公司財務負責人 |
| 客戶專屬 | 科目、核算維度、模板、工作流及例外 | 客戶管理者／顧問 |

### 生命週期

發現變動 → 專業解讀 → 建立草案 → 同行覆核 → 批准 → 設定生效日 → 監測適用 → 替代或退役 → 評估受影響客戶與歷史期間 → 必要時重算。規則更新不得直接覆寫舊版；已批准期間仍能按當時版本重演。

### 研究登錄簿欄位

- 研究問題、所影響功能／資料欄位、目前暫定結論、司法管轄區與準則。
- 一手來源、引用位置、未解問題、專業責任人、同行覆核人。
- 是否阻塞 MVP、目標確認日、確認日期、規則版本及受影響客戶。
- **規則所需的最低資料粒度**（CR-001 新增）。
- AI 可協助搜尋與草擬，但不得自行成為權威法源或在無批准下發布規則。

### 立即訪談問題

- 母公司使用哪一套 ERP／合併工具？確切產品、版本、模組、匯入方式與核算維度是什麼？
- 日本子公司的事業年度是否與母公司一致？目前如何形成母公司曆年期間資料？
- 母公司採直接法還是間接法編製合併現金流？日本端目前能提供到什麼粒度？
- 固定資產是否已有集團口徑第二套折舊？取得、追加、減損與處分歷史是否完整？
- 首次轉換需建立幾年期初與比較資料？導入性質及追溯政策為何？
- 現有流程每月／季／年花多少人工時？最常出錯及反覆詢問的是什麼？
- 哪些調整固定重複、哪些每期判斷？誰準備、覆核、批准與承擔政策決定？
- 母公司審計師目前要求哪些海外子公司轉換底稿？每期補件幾輪、幾件、多久回覆？
- 平台要作正式保存載體、轉換副本還是混合模式？各類資料由誰控制及保存多久？
- 母子公司、關係企業及事務所之間如何收取服務費或代墊？契約和受益證據是否完整？
- **日本端每期能穩定提供哪些科目範圍的仕訳明細？哪些只能提供餘額？**（CR-001 新增）
- **一名職員平常同時負責幾家客戶？切換頻率如何？目前工作做到一半換客戶時怎麼保存？**（CR-002 新增）
- **客戶提供的檔案通常帶有哪些可辨識資訊（法人番号、公司全名、僅簡稱或完全沒有）？是否需要建立別名表？**（CR-002 新增）
- 客戶願意為節省工時、縮短關帳、降低錯誤或改善審計協作支付多少？

### 後續研究待辦；不阻塞目前式樣書

- 按交易類型建立日本 GAAP／日本稅務／CAS 差異清單與分錄範本。
- 取得真實客戶的金蝶產品與匯入規格，驗證可配置模板是否足夠。
- 確定日本電子帳簿保存制度下平台的正式角色及契約、操作要求。
- 驗證跨境服務費、代墊與集團內共享服務的實際收費模型及移轉定價文件。
- 與母公司審計師確認平台作為服務機構／資訊系統時的控制與鑑證路線。
- 用既有案件統計首次導入工時、補件輪次、固定資產重算量與可自動化比例。

## SECTION 23　決策摘要

> 目前先凍結：產品邊界、三基礎／兩橋樑、四類規則、多基礎資料模型、ERP 解耦、人工覆核與可稽核證據。法規細節按是否阻塞 MVP 排序持續補充，不再讓研究取代產品定義。

本手冊保留原研究內容，但將「已確認設計」、「暫定假設」與「待研究事項」分開。v1.0 之後已完成 2 個真實設計循環：基本設計書 §24～§28 定版為 v1.0 並回饋 CR-001；隨後多案件日常作業情境的檢視產生 CR-002，形成本版 v1.2 並將於基本設計書 v1.1 落地。下一步應用 1–2 個真實客戶完成需求訪談、資料樣本與基準數據，再把 P0 寫成 API／檔案契約與測試案例。

**兩次循環的共同教訓**：需求缺口不是出現在「這個功能該不該做」，而是出現在**兩個各自正確的規定相乘之後**——CR-001 是粒度模型與追溯宣稱相乘，CR-002 是自動儲存與計算凍結相乘。定版前的一致性稽核必須檢查交互作用，不能只逐條檢查條文。
