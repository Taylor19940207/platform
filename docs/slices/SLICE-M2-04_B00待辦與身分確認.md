# SLICE-M2-04　B-00 待辦整合與 UNVERIFIABLE 人工確認

**範圍**：`B-00「等我處理的事項」佇列（待身分確認／待覆核／待批准／被退回・待補證據／
未完成草稿）＋ 一鍵回到工作物件 ＋ UNVERIFIABLE 人工確認畫面（寫入不可變 Resolution
與事件 → 依 G-01 決定能否接受）`。不新增任何控制語意——SOD-07 與接受判定式已是
DB 最後防線，本刀補「入口」。

## 本刀凍結的設計決策

1. **佇列定義（全部依指派過濾＋四欄脈絡）**：
   - **待身分確認**：`identity_status = PENDING_CONFIRMATION` 的批次（含已 QUARANTINED
     者不列——隔離批次的出路是重傳，不是確認）。
   - **待覆核**：`adjustment.status = PENDING_REVIEW` 且觀看者可為合格覆核人
     （SOD-01：`prepared_by ≠ 觀看者` 才列入「等我」；自己編製的顯示於草稿區）。
   - **待批准**：`PENDING_APPROVAL` 且觀看者具 R4（AC-WFL-001：`prepared_by ≠ 觀看者`）。
   - **被退回／待補證據**：`DRAFTING` 且最新里程碑為 `RETURNED` 的調整（退回理由分類
     一併顯示）——觀看者為其編製人。
   - **未完成草稿**：觀看者自己 `DRAFTING` 的調整＋自己建立且未批准的映射草稿，
     依最後保存時間排序。
2. **一鍵回位**：每列連到具體工作物件——批次→確認頁／B-04、調整→B-05、
   映射草稿→B-04。B-00 規格「回到上次編輯位置」以「回到該工作物件畫面」為本刀範圍
   （游標級位置屬後續）。
3. **確認頁（掛於 B-03 匯入與資料品質範圍）**：顯示**宣告目標**（客戶×法人×期間，
   含法人權威代碼）、**偵測證據**（SourceIdentityAssessment 全部列：evidence_kind、
   偵測到的識別資訊、match_result、識別規則版本、別名表版本、評估時間——多筆並存
   全部顯示）、**批次版本**與檔案雜湊、**確認理由（必填）**與證據參照（選填）。
4. **資料接受角色＝R2（本刀）**；「客戶政策指定角色」屬後續（政策實體未實作，如實標示）。
   角色不符 → 403＋ControlViolationAttempt。
5. **SOD-07 應用層先判**：上傳者開啟確認頁看得到內容但提交被拒（403＋CVA，
   說明「上傳者不得確認自己上傳的批次，與當下角色無關」）；DB 觸發器仍為最後防線。
6. **確認＝單一交易**：`SourceIdentityResolution` 寫入＋`identity_status →
   MANUALLY_RESOLVED`＋DomainEvent（`import_batch.identity_resolved`，payload 含理由、
   證據參照、識別規則版本、別名表版本＝本刀無別名表故記 `null`）同一 statement／交易。
   確認**不自動接受**——接受仍是獨立動作（G-01 判定式，含 CONFLICT 永拒；CTX-g 正交軸）。
7. **CONFLICT 不出現在待確認佇列、確認頁對 CONFLICT 批次拒絕開啟提交**（CTX-c 三條
   出路文案照 §25.5 顯示）。
8. 佇列查詢全部走既有指派過濾模式（RLS＋`role_assignment`）；不新增資料表——
   本刀零 migration（除非實作中發現缺欄位，屆時於走查回報）。

## 驗收清單

| # | 條件 |
|---|---|
| 1 | B-00 五個佇列各自出現正確項目：待身分確認（PENDING_CONFIRMATION 批次）、待覆核（他人編製的 PENDING_REVIEW）、待批准（R4 且非自己編製）、被退回（自己的 RETURNED→DRAFTING 含理由分類）、未完成草稿（自己的 DRAFTING 調整＋未批准映射草稿） |
| 2 | 每列同時顯示客戶／法人／期間／狀態四欄（WKB-c）；點擊直達對應工作物件（B-03 確認頁／B-04／B-05） |
| 3 | 只顯示有權且被指派的工作（WKB-a）：未指派案件的名稱與計數不出現於任何佇列；撤銷指派後重新載入即消失，既有連結直接存取被拒（WKB-b） |
| 4 | SOD 過濾正確：自己編製的調整不出現在自己的「待覆核／待批准」，出現在對方的佇列（甲編製→乙見待覆核；乙覆核後→丙見待批准、甲不見） |
| 5 | 確認頁完整呈現：宣告目標（含權威代碼）、全部評估列（證據分級、偵測值、規則版本、時間）、批次版本、檔案雜湊、必填理由欄 |
| 6 | 角色閘：非 R2 提交確認 → 403＋CVA；**上傳者本人提交 → 403＋CVA（SOD-07 應用層），直接 SQL 亦被 DB 觸發器拒絕（既有測試）** |
| 7 | 確認成功＝單一交易：Resolution＋identity_status=MANUALLY_RESOLVED＋DomainEvent 同生共死；事件 payload 含理由／證據參照／識別規則版本 |
| 8 | 確認後批次可接受（G-01 三條件）；**確認不自動接受**（CTX-g：確認完成後批次仍為 VALIDATED，需另按接受）；理由空白 → 409 拒絕 |
| 9 | CONFLICT 批次：不入待確認佇列；確認頁提交被拒（CTX-c 無豁免，三條出路文案）；重複確認同一評估 → 409（DB UNIQUE 既有） |
| 10 | 效力只及該批次版本（CTX-e）：重傳新批次（新版本）後其 PENDING_CONFIRMATION 需重新確認，原確認紀錄並存不可覆寫 |
| 11 | 佇列數字誠實：五佇列計數與明細一致；空佇列顯示「無」而非隱藏（使用者能確認「沒有事」與「看不到」的差別） |
| 12 | 全部拒絕保存機器代碼＋人可讀原因（CVA）；既有 427 條零退化 |

## 明確不做（B-00 P1 或後續刀）

背景匯入與計算的技術進度、截止日與逾期、容量分析（§28.3 P1）；自動保存與儲存狀態
（順序第 4 刀）；期間生命週期；別名表管理（R7 維護、R4 批准——確認頁只讀顯示
「本刀無別名表」）；游標級「上次編輯位置」；R1 表面 A；客戶政策指定資料接受角色；
粒度不足升級佇列（INSUFFICIENT_GRANULARITY——escalation 機制屬多基礎／規則刀）。

**流程**：本文件走查通過 → 實作（預計零 migration）→ 三層測試（佇列過濾／SOD 呈現／
確認交易原子性／CTX 子案例補齊）→ Case-001 走查（含 no-id 批次確認→接受全流程）→
更新 handoff → 期間生命週期切片。
