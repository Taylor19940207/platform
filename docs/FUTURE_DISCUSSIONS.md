# 後續討論議題

本文件專門保存**尚未需要立即決策、但未來必須帶著真實證據重新討論的產品議題**。

它不是正式基線、ADR、切片規格或已承諾的開發範圍，不得用來取代
`docs/baseline/` 兩份正式基線。可執行工作仍記入 `docs/BACKLOG.md`；議題形成決策後，
再依 `docs/GOVERNANCE.md` 移入切片、ADR、BACKLOG 或符合例外時提出基線變更。

## 使用方式

每個議題至少記錄：背景、目前暫定方向、尚待回答的問題、需要什麼證據、何時重開討論。
沒有新證據時，不因抽象疑慮反覆推翻既定計畫。

狀態使用：

- `觀察中`：目前不改計畫，持續收集證據。
- `待討論`：已有足夠證據，下一次規劃時需要裁決。
- `已決策`：結論已落入 ADR、切片、BACKLOG 或正式基線，附上連結後保留歷史。

## DISC-001：控制強度與事務所實用性的平衡

- 狀態：`觀察中`
- 建立日期：2026-08-05
- 目前是否改變計畫：否，繼續依既定里程碑與切片順序開發。

### 背景

本產品定位仍是事務所內部使用的中日跨境財務整理、計算與作業平台：職員完成資料整理、
映射、調整與計算，系統保存控制及證據；税理士／具資格責任者完成專業判斷與最終批准後，
才向母集團交付。

RLS、金額精度、來源與版本凍結、職責分離、不可變歷史、稽核軌跡及批准後檔案一致性，
是這類財務交付系統的必要安全與正確性要求，不因產品供內部使用而取消。

需要持續觀察的風險是：如果只實作「不得繞過」，卻沒有相應的退回、更正、補件、重跑、
重新批准與例外裁決路徑，產品可能安全但難以完成日常案件，最後迫使使用者回到 Excel、
電子郵件或請工程師直接改資料。

### 目前暫定方向

1. 現階段不預先弱化底層控制，也不因此推翻既有架構。
2. 先完成可信賴的端到端主流程，再以真實事務所職員與税理士走查驗證可用性。
3. 未來改善體驗時，優先增加合法恢復路徑及清楚指引，不以直接覆寫歷史換取方便。
4. 控制應區分：絕對不可繞過、可由具資格者裁決、提示性檢查；不得把所有警告都做成硬阻擋。
5. 客戶畫面應說明「發生什麼、影響什麼、為何不能繼續、誰能處理、下一步怎麼做」，
   不直接暴露以工程診斷為中心的內容。

### 未來需要回答

1. 一個代表性案件從上傳到可交付，需要多少步驟、角色切換與等待？
2. 哪些硬阻擋在真實案件中最常發生？使用者能否不靠工程師自行恢復？
3. 小額、低風險事項是否被迫走與重大調整相同的批准流程？
4. 哪些情況應允許税理士作成有理由、有證據、可追溯的專業裁決？
5. 使用者是否能理解錯誤原因、影響金額與下一步，而不必理解控制代碼或資料庫概念？
6. 税理士能否在合理時間內看懂差異、未決例外、依據及即將批准的確切輸出？
7. 正式批准後發現錯誤時，更正版、撤回與重新交付流程是否足夠清楚且可操作？

### 重開討論所需證據

- 至少一個代表性真實或充分擬真的完整案件走查。
- 事務所職員與税理士分別操作，而非由開發者代走。
- 記錄完成時間、角色切換次數、被擋次數、求助點與無法自行恢復的步驟。
- 區分畫面／文案問題、缺少恢復路徑、控制分級不當與底層控制本身不合理。
- 若主張弱化控制，必須同時說明替代控制及不會增加的資料、法規或交付風險。

### 建議重開時點

- 第一條可由職員與税理士完整走通的「上傳 → 計算 → 覆核 → 批准 → 正式交付」流程完成後。
- 首次事務所使用者測試後。
- 或在開發期間出現「只能由工程師／直接 SQL 才能恢復案件」的實證時提前重開。
